## 独立検算で発見した事実（B の自己申告の再検証）

### 1. 【最重要・両EXP共通】D-4・D-6 共通先行タスクの不成立を、B は認識しながら停止しなかった

10Y-COMMON §8 は「以下はどちらの EXP の測定よりも前に実施し…**いずれかが不成立なら、実験を回さずに S へ差し戻す**」と明記し、D-4・D-6 それぞれの「不成立時」欄にも例外なく「S に差し戻す」とのみ書かれている（緩和条件・部分適用の余地なし）。

- **D-4（`/fins/summary` の10年カバレッジ）**: 合格条件「年あたりレコード件数が直近年の50%以上」に対し、`d4_d8_common_tasks.json` の実測で **2016年の比率 = 0.38（38%）**。`run.log` は「文字通りの判定は不成立」と明記した上で、2016年・2026年がロールング10年窓の両端で暦年として不完全（2016年は9/16開始で約3.5ヶ月分、2026年は9/15までで約8.5ヶ月分）という**構造的な理由**を挙げ、「閾値・判定式は変更していない」として**そのまま先へ進んだ**。
  - この説明自体は数学的に筋が通っており（部分年は自動的に按分不足になる）、**データ欠損や取得失敗ではなく閾値設計側の見落としである可能性が高い**。しかし spec の文言には「部分暦年は除外して判定してよい」という例外は一切事前登録されていない。B が独自に「これは安全側だろう」と判断して続行したのは、**N-6（PEAD）/N-8（Gap）が明示的に禁止する「自分で安全側だろうと解釈して埋め、差し戻さない」行為そのもの**である。
- **D-6（`AdjFactor`/`ExRT` の調整規約）**: 合格条件「意味が一意に決まる」に対し、`AdjFactor≠1.0` の2,592行のうち `ExRT` の値が `{"1": 1815, "2": 754, "3": 23}` の3種出現し、旧spec前提の対応付け（`ExRT=="1"` ⟺ 分割・併合）は "1" の1,815行についてのみ確認できた。`consistent_ext1_iff_split=False` であり、**777行（30.0%）の意味は未解決のまま**。`run.log` は「この点はSへの差し戻し対象であり」と自ら明記しながら、「本実装ではEXP-OBS000006のE-1除外ロジックを旧定義のまま変更せずに実行した」と**続行を選択**した。
  - サンプル検算（`d4_d8_common_tasks.json` の `sample_verification_top5_codes`）を見ると、`C/AdjC` 比率が `1.9999`/`2.0`、`3.9993`〜`3.9998`/`4.0` のように**理論値の近傍にわずかにばらついた値のクラスタ**として出現しており、浮動小数点の累積誤差である可能性は高い。しかしこれも B・私（C）のいずれも実測で確認していない**推測**であり、777行が実際に権利落ち関連（配当以外の株主割当等）であった場合、**PEAD側では調整系列 `AdjO`/`AdjC` を用いる R5 計算が、Gap側では E-1 除外漏れが `σ_gap`・プール・`z*` 較正に波及する**。

D-4・D-6 とも「不成立時: Sに差し戻す」という**無条件かつ例外のない事前登録規則**に該当する。B が独自の裁量で「影響は軽微だろう」と判断して続行したことは、spec の鉄則（成功基準を回す前に固定し、結果を見てから解釈で埋めない）に反する。**この時点で PEAD・Gap 双方の以降の計算はすべて「停止規則を経ていない状態」で実行されたものであり、G1 の結果がどうであれ、最終確定はできない。**

### 2. G1-2（選定期間 `IC_bar`）不合格そのものは、コード上の実装バグではなく妥当に計算されている（ただし上記1の瑕疵の影響は未検証）

`scripts/pead10y_prediction_unit.py` と `scripts/lib/jq10y_common.py` を読み、`spearman()` 関数がタイを正しく平均順位で処理していること（§6.1 の要求どおり）、`compute_raw_sue_for_code()` が spec §3.1〜3.3 の `A(t)`/`B(t)`/`Scale(t)` 定義を一字一句反映していること、`entry_and_forward()` が `t1`（開示翌営業日）始値エントリー・`t5` 終値での `R5 = AdjC(t5)/AdjO(t1) - 1` を正しく計算していることを確認した。IC_bar の算出自体にサイン反転やオフバイワンの類のバグは見つからなかった。

- **選定期間 `IC_bar = -0.009026`（K=115日）** は、標準誤差を概算（`SD(IC_d)≈1/√(n_d-1)`、選定期間の `n_d` が確認期間平均12前後と近いと仮定すると `SE ≈ 0.31/√115 ≈ 0.029`）すると**統計的にゼロと区別できない水準**であり、「選定期間で負のエッジがある」のではなく「選定期間では何も検出されていない（ノイズ）」と解釈するのが妥当。
- 一方、確認期間 `IC_bar = 0.042023`（p=0.0286）は `IC_econ = 0.35%/(1.755×σ_R)`（実測 `σ_R=4.837%`）で逆算すると `IC_econ ≈ 0.0412` となり、**測定値は経済的必要水準のすぐ上というギリギリの水準**である。
- spec §2.2 が明記する通り、本EXPには選定期間で調整する自由パラメータが一切存在しない（SUE定義・ホライズン・閾値・コストすべて固定）。したがって「選定期間でエッジの兆候すら出ず、確認期間だけ有意」という非対称は、選定/確認が同一の固定設計に対する2つの独立標本である以上、**本来対称的な結果が期待されるところに現れた奇妙な所見**である。G1-2 はまさにこの種のパターンを検出するために事前登録されたゲートであり、**noise-levelの選定期間推定値と、閾値をわずかに上回るだけの確認期間推定値の組み合わせは、trading-app-v2 OBS000019/028型（選定でのみ、あるいは確認でのみ都合よく現れる）の親戚として扱うべき**——ただし今回は「選定で良く確認で消える」ではなく逆方向であり、G1-2 が正しく設計どおりに不合格を検出している。**判定不能ではなく、事前登録された基準に照らして明確な不合格。**

### 3. デシル分析の実装に平均順位タイ処理違反を発見（G1-3/4/5/6/7 に影響。G1-2 には影響しない）

`prediction-unit.json` の `decile_stats_gross` を見ると、**デシル3〜6が全件 `n=0`**（デシル1=345, 2=1870, 3〜6=0, 7=95, 8=322, 9=408, 10=475、合計3515＝全確認期間対象数と一致）。

原因を `pead10y_prediction_unit.py` で特定した:

```python
rank = bisect.bisect_left(s, e["raw_sue"])
pct = rank / n
```

`bisect_left` は同値集団の**最も左（最小順位）の位置**を返す。一方 spec §3.4 は「同値（タイ）は平均順位で処理する」と明記している。`feasibility.json`（9-2）の実測では **`RawSUE` の厳密ゼロが全年で約60〜68%**（中央値=0、p10がほぼ0またはわずかに負）を占める。`bisect_left` を使うと、この巨大なゼロ塊が**すべて同一の（ゼロより小さい値の個数÷nという）1点のパーセンタイルに押し込まれる**——本来「平均順位」であれば `負の値の個数 + ゼロ塊の半分` あたりに位置すべきところを、**タイ集団の最も低い端に全員を寄せてしまう**。これがデシル2に約半分の観測（1870/3515）が集中し、デシル3〜6が空become になる直接の原因である。

- **G1-2（IC_bar）はこの影響を受けない**（`spearman()` は正しい平均順位を内部で使っている。デシル用の `SUEpct` とは別経路で計算されているため）。したがって本項の指摘は**総合判定を変えるものではない**が、G1-3〜G1-7 の一部（特に G1-5 のデシル単調性 `ρ_dec`）は本来10点で評価すべきところ**実質6点（デシル1,2,7,8,9,10のみ）で評価されており、報告値 `ρ_dec=0.7143` は spec が意図した検定と異なるものになっている**。全G1判定はいずれにせよ G1-2 一件の不合格で `all_G1_pass=false` となるため実害は生じていないが、**再実行時に必ず修正すべき実装バグ**として記録する。

### 4. `prediction-unit.json` は存在するが `pipeline.json` は存在しない ― これは正当（差し戻し理由には数えない）

チェックリスト#1（予測単位×パイプライン整合）は形式的には「片方欠落＝自動差し戻し」だが、本件は spec N-8「G1不合格ならG2を測定しない」に明示的に従った結果であり、`run.log` にも「G1不合格のため以降は実行していない（N-8）」と停止理由が明記されている。これは trading-app-v2 OBS000025型（予測単位◎なのにパイプラインを測らず隠す）とは性質が異なり、**予測単位が✕だからパイプラインを測っていない**という真逆のケースである。spec §11 が「DSゲート・G1不合格で停止した場合は pipeline.json の不在が正当」と明記しているため、この点のみを理由に差し戻すことはしない。

## 判定理由

**総合判定は「差し戻し」。** 不採用でも採用可でもない理由:

1. **G1-2 の不合格自体は妥当**（実装バグなし、ノイズと解釈するのが自然）であり、これ単独なら spec §6.8.1 の事前登録文言どおり「不採用」で確定してよい。
2. **しかし D-4・D-6 という共通先行タスクの停止規則が守られていない**（B が問題を認識しながら「軽微だろう」と自己判断して続行した）。これは trading-app-v2 EXP-OBS000037 の教訓（「実装側は spec の矛盾に気づいたら、自分で安全側だろうと解釈して埋めず、即座に差し戻す」）が本PJの `.claude/agents/*.md` に恒久ルールとして反映されているにもかかわらず再発した事例である。
3. 私（C）の評価では D-4・D-6 が G1-2 の符号を覆すほど大きい影響を持つ可能性は低いと見立てるが、**それは私の推測であり、B・Sいずれも実測で確認していない**。spec の鉄則（「実測がこの値だったから閾値をここに置く」形の後付け解釈を禁止する。§7.1など）に照らせば、**私自身が「軽微だろうから見なかったことにする」と判断することもまた同じ罠（HARKing的な基準の恣意的運用）に陥る**。したがって、この瑕疵を理由に**差し戻し**とし、不採用の確定は D-4・D-6 の解消後に持ち越す。

### D-4・D-6 が該当する罠

- trading-app-v2 EXP-OBS000037型（「先読みチェックを通過したことに安心せず、窓・データ整合を自分で検算する」の応用）ではないが、**同じ教訓の別側面**: 「差し戻し規則を見つけたら、影響が軽微に見えても自己判断で押し切らない」。
- 本PJの EXP-OBS000003（旧）で「B が正しく差し戻し、S が独立調査して解消した」という**成功事例**（`portfolio-ledger.md` §実装プロセス上の教訓）とは対照的に、本件は**B が差し戻すべき場面で差し戻さなかった失敗事例**として記録すべきである。

## 差し戻し（該当時）

- **差し戻し先**: B実装チーム（データ層 D-4・D-6 の再検証）。D-4 は構造的な閾値設計の問題である可能性が高いため、解消にはS戦略チームによる spec 文言の扱い決定（暦年按分を考慮した代替判定式を新規事前登録するか、現行閾値を維持したまま「構造的説明が成立する場合は目視確認のみで可とする」旨を明示的に事前登録するか）が必要。
- **内容**:
  1. **D-6（最優先）**: `ExRT="2"`（754行）・`ExRT="3"`（23行）の意味を J-Quants の公式スキーマ・サポート等で確認し、一意な対応付けを確定する。確定できない場合、当該777行が属する銘柄・日について E-1相当の除外が必要かどうかを判定し、PEAD側の `AdjO`/`AdjC` 系列への影響（該当銘柄の調整済みリターンが汚染されていないか）を実測で確認する。
  2. **D-4**: 「年あたりレコード件数が直近年の50%以上」という閾値が、10年ロールング契約窓の両端（部分暦年）を想定していなかった設計上の見落としである可能性が高いことをS戦略チームに報告し、(a) 閾値算式を暦日按分ベースに修正して新規事前登録するか、(b) 現行閾値のまま「境界年の構造的な未達は不成立と扱わない」ことを事後ではなく新たな事前登録として明記するかを判断してもらう。**いずれにせよ、B が独自解釈で継続することは今後禁止**（N-6/N-8 の再徹底）。
  3. **デシルのタイ処理バグ修正**: `pead10y_prediction_unit.py` の `decile_of`/`SUEpct` 計算を `bisect_left` から spec §3.4 の「平均順位」処理へ修正し、デシル1〜10が実データの分布に即して埋まることを確認した上で再実行する。
  4. 上記1〜3の解消後、G1（特に G1-2 とデシル関連の G1-3〜G1-7）を再実行し、**結果が変わらないこと（またはどう変わったか）を新しい `prediction-unit.json` として再納品**すること。
