## 1. 仮説（1文）

**決算短信で開示される会社通期予想に対する四半期累計実績の進捗乖離（＝会計サプライズ SUE-P）は、日本株 TOPIX500 相当ユニバースにおいて、決算発表日の翌営業日寄りから最大10営業日のロング保有の将来リターンを、往復コスト控除後も正の期待値が残る強さで予測する。**

予測変数は会計値のみから決定的に算出され、価格・出来高・テクニカル指標を一切含まない。

### 2.2 ユニバース定義（数値で固定・決定的）

以下を**全て**満たす銘柄を候補とし、**直近20営業日の平均売買代金（`Va`）の降順で上位175銘柄**を採る（175に満たない場合は該当する全銘柄。**閾値を動かして175に合わせにいってはならない**）。

1. `/equities/master` の `ScaleCat`（規模区分）が **TOPIX Core30 / Large70 / Mid400 に相当する区分**（＝TOPIX500 相当）
2. `Mrgn`（信用取引区分）が **制度信用の対象**（貸借銘柄または制度信用銘柄）
3. 判定基準日（後述）から遡る**直近20営業日の平均終値が 1,000円以上 3,000円以下**
4. 判定基準日から遡る**直近20営業日の平均売買代金 `Va` が 5億円以上**

**判定基準日と固定タイミング（先読み防止）**:
- ユニバースは**決算シーズン単位で固定する**。各決算シーズン（§3.2 で定義）について、そのシーズンで最初に出現する `DiscDate` の**20営業日前**を判定基準日とし、そこから遡る20営業日のデータのみで条件3・4を判定する。
- 一度確定したユニバースはそのシーズン中変更しない。

**条件3・4は価格情報を使う唯一の箇所である。** これは「建てられるか」を決める**執行制約**であり予測変数ではない。以下3点を厳守する（必須条件②の趣旨を守るため）。
- (i) シーズン開始時点で固定し、(ii) シーズン中は変更せず、(iii) **予測変数（§3）の構成には一切使わない。**

**`ScaleCat` の実際のラベルは未確認である。** B実装は `ScaleCat` のユニーク値を全列挙して `params.json` に記録し、TOPIX500 相当の集合を確定すること。想定と異なるラベル体系だった場合、**独自判断で埋めずに S戦略チームへ差し戻す**（EXP-OBS000037 の教訓）。

**生存バイアス**: `/equities/master` は取得時点の上場銘柄一覧である可能性が高い。上場廃止日に相当するフィールドの有無を確認し、無ければ「期間中に上場廃止した銘柄が欠落しており生存バイアスが残存する」ことを `params.json` に明記すること（隠さない）。

### 2.3 予測変数（入力）

**SUE-P（進捗率サプライズ）＝ 主指標。** 定義は §3.1。会計値のみから算出する。

**SUE-R（会社予想改訂サプライズ）＝ 事前登録した副指標。** 定義は §3.3。**記録するが、単独で G1 合格を生じさせない**（多重検定の回避）。

### 2.4 禁止する入力（必須条件①②の実装）

以下を予測変数として**一切使わない**。1つでも混入した時点で本 EXP はエッジ族の純度を失い、PJ000001 §4 C-3 の低事前確率族に落ちる。

- 発表日の異常リターン（abnormal return）・発表日リターン・発表日出来高・出来高変化率
- 株価リターンのボラティリティによる正規化（**標準化の分母に価格を使わない**）
- 時価総額による正規化（時価総額は価格由来）
- モメンタム、移動平均、MACD、RSI、ボリンジャーバンド、CCI、ADX、ATR、Stochastic、その他一切のテクニカル指標
- 決算短信テキストの LLM スコア（③LLM単独スリーブとして別 EXP。本 EXP のスコープ外）
- ②シグナル層の出力との合成・フィルタ・重み付け（**必須条件①**）

**注**: §4.2 のトレーリングストップは**⑤リスク管理層の決済ルール**であり、②のシグナルではない。エントリーの可否・方向は SUE-P のみが決める。

## 3. SUE の定義（S-1 の確定）

### 3.0 prescreen 前提からの逸脱とその理由（隠さず明記する）

prescreen §「正規化の純度について」は「SUE の標準化には**過去複数期の予想誤差の標準偏差**を用いる」としていた。**この定義は本実験のデータ制約下では算出不可能である。**

- 利用可能なデータは 2024-06-21 以降であり、選定期間の先頭（2024年8月の1Q決算）時点で過去の予想誤差の履歴は**ゼロ期**である。
- 「過去4期の予想誤差の標準偏差」を分母に置くと、**選定期間のほぼ全域でサプライズが定義できず、実験が成立しない。**
- 同じ理由で「前年同期の進捗率を基準とする季節性調整」も選定期間では使えない（前年同期のデータが契約範囲外）。

したがって本 spec は、**単一の開示レコードと直前の開示レコードのみから決定的に算出でき、かつ価格を含まない**サプライズ定義を採る。これは prescreen の意図（会計データのみで正規化する）を保ちつつ、データ制約に適合させた措置である。**この逸脱は C品質チームの検証対象とする。**

**副作用として残る弱点（正直に書く）**: 企業固有の期内季節性（期初集中型／期末集中型）を除去できない。これはノイズ源であり系統的バイアスではないが、IC を押し下げる方向に働く。除去できていないことを `params.json` に明記すること。

### 3.1 SUE-P（進捗率サプライズ）— 主指標

イベント `i`（銘柄 `Code` × 開示 `DiscNo`）について、以下の手順で決定的に算出する。

| 手順 | 内容 |
|---|---|
| 1 | **対象利益項目 = 営業利益。** 実績は `OP`、会社予想は `FOP`（いずれも連結）。連結値が欠損の銘柄は非連結 `NCOP` / `FNCOP` を使い、**どちらの系列を使ったかをイベント単位で記録する**。両方欠損のイベントは除外 |
| 2 | **累計実績 `OP_i,t`**: 当該開示が報告する期首 `CurFYSt` から `CurPerEn` までの累計営業利益（開示された値をそのまま使う。四半期単独値への分解はしない） |
| 3 | **基準となる会社予想 `FOP_i,prev`**: **同一決算期（`CurFYEn` が一致）について、イベント `t` の直前の開示（`DiscDate` が `t` より前で最大のもの）で公表されていた通期営業利益予想。**<br>**`FOP_i,t`（今回の開示で同時に出た改訂後予想）は使わない。** 改訂後を使うと実績と予想が同時に動き、サプライズが機械的に縮小する |
| 4 | **除外規則**: 直前の開示が存在しない（＝データ範囲の先頭にかかる）イベントは除外。`FOP_i,prev ≤ 0`（赤字予想・ゼロ予想）のイベントは進捗率が定義できないため除外。除外件数を種別ごとに記録する |
| 5 | **進捗率** `P_i,t = OP_i,t / FOP_i,prev` |
| 6 | **四半期区分** `q ∈ {1, 2, 3}` を `CurPerType` から取る。**本決算（FY, q=4）は対象外**（通期予想が確定値になり進捗率が 1.0 近傍に張り付くため。かつ本決算開示は翌期予想の同時開示という別種の情報を含み、混合になる） |
| 7 | **生サプライズ** `RawSUE_i,t = P_i,t − q/4` |
| 8 | **外れ値処理**: `RawSUE` を選定期間の分布の **1%点・99%点で winsorize** する。この2つの境界値は**選定期間で一度だけ算出して凍結**し、確認期間ではその凍結値を使う（確認期間の分布を見ない） |

**イベント抽出規則（決定的）**:
- `DocType` のユニーク値を全列挙して `params.json` に記録し、**決算短信に相当するものだけ**を採る
- 同一 `(Code, CurFYEn, CurPerType)` に複数レコードがある場合（訂正開示等）は **`DiscNo` が最小＝最初の開示**を採用。訂正開示はイベントとしない
- 採用レコード数・除外レコード数を理由別に記録する

### 3.2 決算シーズンの定義

`DiscDate` を昇順に並べ、**開示が15営業日以上途切れた箇所でシーズンを区切る**。各シーズンに連番を振り、`params.json` に「シーズン番号・開始日・終了日・イベント件数・ユニークDiscDate数」を記録する。

prescreen は「年4シーズン × 約15営業日」と概算したが（要確認 R-6）、**この前提は実データで検証すること。実測がこれと大きく食い違う場合は、数値を独自に読み替えず結果に併記する。**

### 3.3 SUE-R（会社予想改訂サプライズ）— 事前登録の副指標

`SUE-R_i,t = (FOP_i,t − FOP_i,prev) / TA_i,t`

- `FOP_i,t` = 今回の開示で公表された通期営業利益予想、`FOP_i,prev` = §3.1 手順3 と同じ
- `TA_i,t` = 総資産（今回の開示の `TA`。連結欠損時は `NCTA`）。**総資産は会計値であり価格を含まない**（時価総額を使わない理由）
- winsorize は SUE-P と同じ手続き（選定期間の1%/99%点で凍結）

**SUE-R は記録専用である。** SUE-R の結果を根拠に G1 を合格にしてはならない。仮に将来 SUE-P と SUE-R の両方を意思決定に使う場合は、Bonferroni 補正により各 α = 0.025 とする。

## 4. 約定モデル（S-2 の確定）

### 4.1 時系列ウィンドウの定義 — 「本数」と「対象範囲」の算術的対応

> **EXP-OBS000037 の教訓（`portfolio-ledger.md` 参照）に基づく必須記述。**
> 以下の対応表と矛盾する解釈をしてはならない。矛盾・曖昧さを見つけた場合、**B実装は独自解釈で埋めずに即座に S戦略チームへ差し戻すこと。**「安全側だろう」という推測は、必ずしも安全側に働かない。

**基準の定義**:
- **イベント日 `t` = `DiscDate`**（開示日そのもの）
- **営業日のカウントは、当該銘柄の日足バーが存在する日で行う**（`/equities/bars/daily` にレコードがある日）。`t` より後の最初のバーの日を **D+1**、次を D+2 … と定義する
- `t` 当日のバー（もし存在すれば）は **D+0** であり、**D+1 には含めない**

**対応表（これが唯一の正）**:

| ホライズン `h` | 建玉の期間 | 使う日足バー | **バーの本数** | リターン算出に使う価格 | **使う終値の個数** | **終値間の隣接日次リターンの本数** |
|---|---|---|---|---|---|---|
| h=1 | D+1 寄り → D+1 引け | D+1 | **1本** | `O_{D+1}`, `C_{D+1}` | 1個 | **0本** |
| h=3 | D+1 寄り → D+3 引け | D+1〜D+3 | **3本** | `O_{D+1}`, `C_{D+3}` | 3個 | **2本** |
| **h=5（主）** | D+1 寄り → D+5 引け | D+1〜D+5 | **5本** | `O_{D+1}`, `C_{D+5}` | 5個 | **4本** |
| h=10 | D+1 寄り → D+10 引け | D+1〜D+10 | **10本** | `O_{D+1}`, `C_{D+10}` | 10個 | **9本** |

**言い換え（冗長だが意図的に重複して書く）**:
- 「**h 営業日保有**」とは、**D+1 から D+h までの日足 h 本**を使い、`O_{D+1}` で建て `C_{D+h}` で手仕舞うことを指す。
- **h 本のバーからは h 個の終値が得られ、終値間の隣接日次リターンは h−1 本である。**
- G1 の予測対象リターンは **始値→終値の1本の区間リターン**であり、隣接日次リターンの積や和ではない。

**先読みの排除**:
- `O_{D+1}` は `t` の開示より必ず後に成立する価格である（`DiscTime` が場前・場中・場後のいずれでも、D+1 の寄りは情報公開後）。したがって **D+0 のバーを一切使わない本設計は、`DiscTime` の値によらず先読みを構造的に排除する。**
- **`DiscTime` を使ってエントリー日を早めてはならない**（場前開示だけ D+0 寄りで建てる、等）。統一して D+1 寄りとする。
- ただし `DiscTime` の分布（場前 < 9:00 / 場中 9:00〜15:30 / 場後 > 15:30 の件数）は**診断として必ず記録する**。また 場前/場中/場後 の3群別の IC も**記録のみ**行う（合否判定には使わない）。

**バー不足イベントの除外**: D+10 のバーが存在しないイベント（期間末尾・上場廃止等）は G1・G2 の**両方から除外**し、件数を記録する。

### 4.2 エントリー

| 項目 | 固定値 |
|---|---|
| タイミング | **D+1 の寄り（始値 `O_{D+1}`）**。場前・場中・場後のいずれの開示でも統一 |
| 約定価格 | `O_{D+1} × (1 + 片道スリッページ 0.075%)` |
| **約定不能判定（値幅制限）** | `O_{D+1} == UL_{D+1}`（ストップ高で寄る）または `Vo_{D+1} == 0`（出来高ゼロ）の場合、**当該イベントはエントリー不成立**とする |
| 約定不能時の扱い | **D+2 以降に追いかけない。当該イベントは破棄する。** 破棄件数・破棄した事象の SUE-P 値・仮に `O_{D+2}` で建てられたとした場合の h=5 リターンを**必ず記録する**（選択バイアスの大きさの測定） |

`UL` / `LL` は `/equities/bars/daily` のレスポンスに含まれるフィールド（実測済み: `Date,Code,O,H,L,C,UL,LL,Vo,Va`）を使う。

### 4.3 トレーリングストップ 4パラメータ（PJ000001 C-1 決着の必須条件）

| # | パラメータ | **固定値** |
|---|---|---|
| 1 | **初期損切幅** | エントリー約定価格から **−3.0%** |
| 2 | **トレール発動水準** | **終値ベースの含み益が +3.0% 以上**になった最初の日の引け後から発動 |
| 3 | **追随幅** | 発動後、**発動日以降の日足終値の最高値から −3.0%** の水準にストップを置く。最高値更新のたびに切り上げ、**一度上げたストップは切り下げない** |
| 4 | **更新足と約定価格** | §4.4 の日次ループに従う |

### 4.4 日次ループ（保守側に倒した約定モデル）

**設計原則: 有利方向の判定は終値のみ（＝遅い）、不利方向の判定は日中値（＝早い）。** この非対称性が「日足のみの検証で約定価格を楽観視しない」ための保守化である（PJ000001 C-1 の警告への対応）。

日 `d`（d = D+1, D+2, …, D+10）について、以下の順序で処理する。

```
Step 0（D+1 のみ）: §4.2 に従いエントリー。約定価格 E を確定。
                    ストップ水準 S ← E × (1 − 0.030)
                    高値基準 HW ← 未設定（トレール未発動）

Step 1（寄り・ギャップ判定）:
    if O_d <= S:
        → ストップを素通りしてギャップ下寄り。約定価格 = O_d（不利を全額受ける）
        → ただし O_d == LL_d（ストップ安で寄る）の場合は「当日約定不能」とし、
          Step 4 をスキップして翌営業日へ持ち越す（§6.2）
        → 決済して終了

Step 2（日中・ストップヒット判定）: ※日中安値 L を使う（不利方向は早く判定）
    if L_d <= S:
        → 約定価格 = S × (1 − ストップ執行の追加スリッページ 0.10%)
        → ただし L_d == LL_d かつ C_d == LL_d（ストップ安比例配分）の場合は
          「当日約定不能」とし、翌営業日へ持ち越す（§6.2）
        → 決済して終了

Step 3（時間切れ判定）:
    if d == D+10:
        → C_{D+10} で決済（時間切れ決済）。決済して終了

Step 4（引け・トレール水準の更新）: ※終値 C のみを使う（有利方向は遅く判定）
    含み益率 = C_d / E − 1
    if トレール未発動 and 含み益率 >= 0.030:
        トレール発動。HW ← C_d
    if トレール発動済み:
        HW ← max(HW, C_d)          ※日中高値 H は使わない
        S  ← max(S, HW × (1 − 0.030))  ※ストップは切り下げない
```

**日中高値 `H_d` はトレールの切り上げに一切使わない。** これはトレールが有利に切り上がるのを遅らせる措置であり、意図的な保守化である。

### 4.5 決済の3バケット（必ず分類して出力する）

全トレードを以下の3つに排他的に分類し、件数・平均リターン・中央値・標準偏差を出力する。

| バケット | 定義 |
|---|---|
| **損切決済** | トレール未発動のまま Step 1 / Step 2 で決済 |
| **トレール決済** | トレール発動後に Step 1 / Step 2 で決済 |
| **時間切れ決済** | Step 3（D+10 引け）で決済 |

**発動水準 +3.0% と追随幅 3.0% が等しいため、トレール決済の最悪値は概ね建値である。** したがって期待値は次式に分解される。B実装はこの3項の実測値を必ず出力すること。

```
期待値 = 損切率 × 損切平均 + トレール率 × トレール平均 + 時間切れ率 × 時間切れ平均
```

### 4.6 損益分岐勝率の再計算（S-8）

## 5. 成功 / 不採用の数値基準（回す前に確定・ロック済み）

**すべて確認（未見）期間で判定する。** 選定期間の数値は閾値凍結とサニティのために使うのみで、合否判定には使わない。

### 5.1 G1（予測単位）— 合否ゲート

**対象**: SUE-P（RawSUE、winsorize 後）と **FwdRet5**（= `C_{D+5} / O_{D+1} − 1`、**手数料ゼロのグロス**、トレール・損切を一切かけない生のリターン）。

**主ホライズンは h=5 のみ。** h ∈ {1, 3, 10} は事前登録した副ホライズンであり、**記録するが、h=5 の不合格を救済してはならない**（多重検定の回避）。

| 条件 | 判定基準 |
|---|---|
| **(a) 主** | Spearman 順位相関 **IC > 0** かつ **日付ブロック permutation（§5.2 の P1）の片側 p < 0.05** |
| **(b) 必須の追加条件** | 選定期間で凍結した上位20%点閾値（§5.3）以上の群について、**FwdRet5 のグロス平均 > 0** |
| **(c) 副・下限ゲート** | RawSUE 十分位（10分位）別の FwdRet5 平均に対する **Spearman(デシル番号, デシル平均リターン)** を算出する。<br>・**この値が負（逆単調）の場合、(a)(b) を満たしていても G1 は不合格**（OBS000018 型の蜃気楼）<br>・**0 以上であれば (c) 単独では不合格にしない。値は必ず記録する** |

**G1 合格 = (a) かつ (b) かつ (c) が負でないこと。**

**Kill 基準（PJ000001 §5.3 / §5.4）**:
- **G1 不合格 → 即打ち切り。** `portfolio-ledger.md` の「不採用」へ負の資産として記録する。
- **B実装は G1 と G2 を同一実行で出力してよい**（API レート制限の都合）。ただし **C品質チームは必ず G1 を先に判定し、G1 不合格の場合は G2 の数値を見ずに Kill を宣告する。**
- **選定期間で RawSUE 上位20%群のグロス平均が負** → その時点で Kill（探索段階でエッジ不在のものを確認期間で測る意味がない）。

**検定力不足による「判定保留」**:
- 確認期間の **G1 有効イベント数 < 300件**、または **ユニーク `DiscDate` ブロック数 < 60** の場合 → **「判定保留（データ不足）」**とする。**合格とも不合格とも宣告しない。**
- この場合は本 EXP を `portfolio-ledger.md` の「保留」へ記録し、解消条件（データ期間の拡張 or 有料プラン）を明記する。

### 5.2 permutation 検定の手続き（必須条件③の実装）

**同日発表銘柄を1ブロックとして扱う。名目 n を有効 n と読んではならない。**

#### P1（主・G1 の p 値はこれを使う）: 日付ブロックの巡回シフト

1. ユニーク `DiscDate` を時系列昇順に並べ、ブロック `B_1, …, B_K` とする
2. 各ブロック内でイベントを**銘柄コード昇順**に並べる（決定的。seed 不要）
3. シフト量 `k ∈ {1, …, K−1}` について、ブロック `B_j` の **SUE-P ベクトル**に、ブロック `B_{(j+k) mod K}` の **FwdRet5 ベクトル**を対応づける。サイズが異なる場合は先頭から `min(n_j, n_{j+k})` 件を対応づけ、余りは当該シフトでは捨てる（**捨てた件数を記録する**）
4. 各 k についてプールした Spearman IC を計算し、`IC_k` とする
5. **片側 p = (1 + #{k : IC_k ≥ IC_obs}) / K**

**この手続きは seed を使わず完全に決定的である。** 確認期間で K ≈ 120 が見込まれ、p の分解能は約 0.008 であるため p < 0.05 の判定には十分である。**K < 40 の場合は p の分解能（1/K > 0.025）が不足するため、その旨を明記し P2 を併記すること。**

#### P2（副・記録必須）: ブロック内シャッフル

同一 `DiscDate` ブロック内で FwdRet5 をランダム置換し、プールした Spearman IC を再計算する。**10,000回、seed = 20260913（固定）**。片側 p を記録する。ブロックサイズ1のイベントは置換で不変のため P2 の計算対象から除外し、除外件数を記録する。

#### P3（参考・記録必須）: 日付ブロックのクラスターブートストラップ

`DiscDate` ブロックを復元抽出で 10,000 回リサンプルし（**seed = 20260913**）、IC の 95% 信頼区間を算出する。下限が 0 を上回るかを記録する（**合否基準ではない**）。

#### 有効 n の報告（必須）

`prediction-unit.json` に以下を必ず含める。
- 名目イベント数、ユニーク `DiscDate` ブロック数 K、平均ブロックサイズ、最大ブロックサイズ
- ブロックサイズの分布（サイズ1のブロック数を含む）
- P1 で捨てた対応づけの件数

### 5.3 G2（パイプライン統合）— 合否ゲート（必須条件④）

**Sharpe の統計的有意性を合格基準に置かない。** 2年の観測から年率 Sharpe を推定した際の標準誤差は概ね `sqrt(1/2) ≈ 0.71` であり、有意性を主張することは原理的にできない（prescreen §(c)）。**言えないことを言えると偽らない。** Sharpe の再現性判定は STEP3 フォワード較正へ送る。

**エントリー判定ルール（意思決定時に知りうる情報のみで構成）**:

- [ ] `DiscTime` の場前／場中／場後の判定はこの取引時間を基準とする（§4.1 の診断記録用）

### 6.6 信用取引関連

## 7. 選定 / 確認プロトコル（S-6 の確定）

### 7.1 主: 時期分割（A案）

| 区分 | `DiscDate` の範囲 | 追加条件 |
|---|---|---|
| **選定（探索）** | **2024-06-21 〜 2025-06-30** | **かつ D+10 のバー日 ≤ 2025-06-30** |
| **確認（未見）** | **2025-07-01 〜 2026-06-21** | **かつ D+10 のバー日 ≤ 2026-06-21** |

**イベントの帰属は `DiscDate` で決める。** 選定期間のイベントで保有窓（D+1〜D+10）が 2025-07-01 以降に及ぶものは、**確認期間の価格データに触れることになるため選定側の分析から除外する。** 同様に確認期間のイベントで D+10 が 2026-06-21 を超えるものは除外する。除外件数を記録する。

**確認期間には選定作業で一切触れない。** 具体的に、以下は**すべて選定期間のデータのみ**で決定し、凍結してから確認期間に適用する。

| 凍結する値 | 決定方法 |
|---|---|
| `RawSUE` の winsorize 境界（1%点・99%点） | 選定期間の分布 |
| エントリー閾値 θ（上位20%点） | 選定期間の分布 |
| 単調性チェック用の5閾値（上位10/20/30/40/50%点） | 選定期間の分布 |

**それ以外（§3 の SUE 定義、§4 の約定モデルとトレール4パラメータ、§6.3 のリスク上限、§5 の合否基準）は本 spec で既に数値固定済みであり、選定期間を見て決めることすら行わない。**

### 7.2 補助: 銘柄分割（B案）

- 175銘柄を**銘柄コードの昇順に並べ、先頭から交互に群A / 群B へ配分する**（1番目=A、2番目=B、3番目=A、…）。**seed を使わず決定的であり、コード体系が業種順であることを利用して業種バランスも概ね保たれる。**
- **B案は単独では使わない。** 時期分割（A案）の確認期間で G1 に合格したものについて、**群A / 群B それぞれで IC を再計算し、両群で同符号かつ両群とも IC > 0 であるか**を追加確認する。
- **B案の結果は G1 / G2 の合否基準ではない。** 記録し、C品質チームの判断材料とする。

### 7.3 測定範囲の空白（明示する）

| 空白 | 内容 |
|---|---|
| **テール局面** | 利用可能な2年間に含まれるテール事象は **2024年8月上旬の急落局面が実質1件のみ**。レジーム別の有意性を主張できる有効 n は存在しない。コロナショック級の局面は測定範囲外 |
| **Sharpe の有意性** | 2年の観測では年率 Sharpe 推定の SE ≈ 0.71。**確認期間の Sharpe が有意に正であることは原理的に示せない**（§5.3 の必須条件④の根拠） |
| **G3 / G4** | スリーブ在庫ゼロのため判定不能（§5.4） |
| **信用規制（日々公表・増担保）** | データが取得できず模擬不能（§6.6） |
| **企業固有の期内季節性** | SUE-P の定義上除去できていない（§3.0） |
| **生存バイアス** | マスタが現時点の上場銘柄一覧である場合、期間中の上場廃止銘柄が欠落（§2.2） |

**これらの空白は STEP3 フォワード較正（90暦日）で部分的に補完する。** バックテストの合格だけで本番反映の根拠としない（PJ000001 §6.1）。

## 8. 測定範囲・データ取得

### 8.1 R-1d（日足の全期間連続性）の継続確認 — 実装の最初のステップ

**条件⓪のうち R-1d のみ部分解消（契約開始日〜2024-10-01 の5ヶ月連続を確認）である。** B実装は、他の作業に入る前に以下を実施すること。

2. **銘柄 × 月 のカバレッジ表**（各月の営業日数に対するバー取得率）を集計し、`params.json` に記録する
3. **欠測月（取得率が 50% 未満の月）が1つでも存在する場合、実装を進めずに S戦略チームへ差し戻す**

当初の「全25点データなし」は HTTP 429（レート制限）が原因と判明している。したがって、**取得は必ず指数バックオフ付きリトライと `data/cache/` へのローカルキャッシュを併用し、429 を「データなし」と誤記録しない**こと。429 とデータ欠損は `run.log` で区別して記録する。

### 8.2 レジーム別分解

**要**（記録のみ。§5.3 の通り合否根拠にしない）。

- 2024年8月の急落局面が選定側・確認側のどちらに入るかを実データで確定する（R-4）
- 3月決算企業の比率および決算発表の集中度を実測し、prescreen の前提「年4シーズン × 約15営業日」の妥当性を検証する（R-6）

### 8.3 予測単位とパイプライン統合の両方を測定する

**片方だけの出力は自動的に差し戻しとする**（PJ000002 §6）。`prediction-unit.json` と `pipeline.json` の両方が揃っていることが完了報告の前提である。

## 10. 本 spec で残る既知の弱点（無理に GO へ寄せない）

prescreen §「正直に認める弱点」を引き継ぎ、spec 段階で判明したものを追加する。

1. **単体で North Star（Sharpe 1.0）には届かない見込み。** 資本制約から年約68トレード・単体 Sharpe 0.35〜0.50 と概算される。PEAD は「これで勝つ」主軸ではなく、ポートフォリオの1スリーブである
2. **2年のデータでは Sharpe の有意性を示せない**（SE ≈ 0.71）。G2 の合格は「平均が正であること」までしか主張しない
3. **G3 / G4 が判定不能**（スリーブ在庫ゼロ）
4. **モメンタム的性質を持つことは否定できない。** 入力は非価格だが「イベント後の一方向継続を取る」出力形は TSMOM と同型である。trading-app-v2 の枯渇診断が出力形にまで及んでいた場合、PEAD も同じ天井に当たる
5. **OBS000025 型の罠（予測単位◎・パイプラインで死亡）を最も踏みやすい設計である。** §5.5 の生データ出力はこれを見逃さないための装置である
6. **【spec 段階で新たに判明】古典的 SUE（過去の予想誤差の標準偏差で正規化）はデータ期間2年では算出不可能であり、進捗率ベースの代替定義を採った**（§3.0）。企業固有の期内季節性が除去できておらず、IC を押し下げる方向に働く
7. **【spec 段階で新たに判明】信用規制（日々公表・増担保）を模擬できない。** サプライズ大の銘柄ほど規制対象になりやすいため、**実運用は本結果より不利になりうる**
