## 3. エッジ検定の開始条件（すべて満たすまで EXP として起票しない）

蓄積したデータで**エッジを測ろうとしてよい**のは、次の4条件を**すべて**満たしたときだけである。満たして初めて、通常のリレー（S:prescreen → S:spec → B:実装 → C:判定）に乗せた**新規EXP**として起票する。

| # | 条件 | 閾値 | 出自（本PJで既に確定済みの閾値の再利用） |
|---|---|---|---|
| **ST-1** | 蓄積営業日数 | **≥ 245営業日** | 1年（PJ000001 §6.1 の蓄積規律の年次単位） |
| **ST-2** | 相異なるイベント日数 | **≥ 100日** | EXP-OBS000003 **DS-6 と同値** |
| **ST-3** | 最大単日シェア | **≤ 25%** | EXP-OBS000003 **DS-7 と同値** |
| **ST-4** | 総イベント件数 | **≥ 300件** | EXP-OBS000001 **DS-1 と同値** |

**ST-A（測定単位の明記・重要）**: ST-2〜ST-4 の「イベント」とは、**その新規EXPが事前登録するイベント定義に合致した件数**であり、**蓄積した開示の総件数ではない**。
例: イベント定義が「業績予想の修正開示」なら、蓄積された全開示ではなく、`doc_category = "earnings_forecast_revision"` に該当した件数で ST-2〜ST-4 を測る。
**蓄積の生件数は ST-2〜ST-4 の上限を与えるだけであり、達成を意味しない。** 本PJは EXP-OBS000001 と EXP-OBS000003 の2件連続で、生件数は足りていたのに「相異なるイベント日」で落ちている（C-7）。同じ取り違えを繰り返さないため、本条を明記する。

**ST-B（参考実測・2026-09-14 時点）**: U-LLM 271銘柄の開示は **1営業日あたり 18.5件**（30営業日・554件の実測）。245営業日で約4,500件が見込まれ、**ST-4（300件）は生件数ベースでは大きな余裕がある。拘束条件になるのは ST-2（相異なるイベント日）である**——イベント定義を絞るほど日数が減るため、EXP 起票時には「イベント定義を絞ること」と「ST-2 を満たすこと」が正面からトレードオフになる。**このトレードオフを、蓄積結果を見てから有利な側に動かすことを禁じる**（イベント定義は prescreen 段階で先に固定し、その後に件数を数える）。

**ST-C（緩和の禁止）**: ST-1〜ST-4 は**本PJが既に確定済みの閾値をそのまま再利用**したものである。**「フォワードだから」「1年待ったのだから」という理由で緩めることを禁じる。** 緩めた瞬間、本トラックは C-7（検出力不足）から逃げただけのものになる。

|---|---|

| 基準日 | **2025-07-01**（PEAD 確認期間の開始日） |
| 銘柄数 | **271銘柄** |
| 参照 | `research/EXP-OBS000001/10-result/universe.json` の `confirmation_universe.main_band_pass_count` = **271** と一致することを検算済み。同ファイルの `codes`（175銘柄）が U-LLM の**部分集合**であることも検算済み |
| 凍結ファイル | `research/_snapshots/llm_features/frozen/universe_v1.json`（`codes_sha256 = 07f86898bcbd8fb53b9e0380fff4036138e06256fbd57339e7bdf97550eacd6f`） |
| 再生成 | `python3 scripts/llm_features_build_universe.py`（`data/raw/pead/` のキャッシュのみを読み、ネットワークに出ない決定的処理） |

**なぜ 175 ではなく 271 か**: 175 は U-6（建玉可能数に由来する**執行側の**上限）を適用した後の数である。本トラックは**ポジションを取らない**ため執行側の上限を継承する理由がなく、175 に絞ることは将来の EXP の選択肢を**不可逆に**狭める（back-fill 禁止により、後から広げても過去分は取り戻せない）。一方で 271 への拡張による費用増は月額 ¥250 程度（§7）にとどまる。

**なぜ全市場（1営業日312件）ではないか**: §7 の実測コスト算術による。全市場を対象にすると **US$83/月 ≒ ¥12,472/月**となり、**C-6 が「払えない」と判定した TDnetアドオン ¥11,000/月 とほぼ同額の壁に、別の名前で戻ることになる**。U-LLM 271銘柄なら **¥807/月**で、同じ壁を1/15の費用で回避できる。

**ユニバース外の開示の扱い（申し送り）**: ユニバース外の本文テキストは `scripts/snapshot_tdnet_text.py` が ¥0 で保存し続けるため、**テキストは失われない**。ただし **LLMラベルは失われる**（back-fill 禁止のため後から付けられない）。将来ユニバースを広げる判断をした場合、広げた時点からの新規分だけが対象となる。**この非対称性を承知のうえで 271 を選んでいる。**

## 5. 凍結②: モデルID・プロンプト・出力スキーマ・APIパラメータ

### 5.1 モデルID

| 項目 | 値 |
|---|---|
| **リクエストに用いるモデルID** | **`claude-haiku-4-5`** |
| エイリアスか | Anthropic の現行モデル表においてこれは**そのまま完全なモデルID**であり、日付サフィックスを付けない表記が正である（`claude-api` スキルの明示規定）。ただし本PJは**文字列の固定だけでは「エイリアス禁止」の趣旨を満たさない**と考え、下記 **M-3** を併用する |
| **M-3（実体の固定）** | **毎回の応答の `model` フィールドを全レコードに記録する。** 最初に成功した呼び出しの値を `manifest.json` の `model_served_frozen` として確定し、以後これと異なる値が返った時点で**即時停止**する（`llm_feature_extract.py` の G-6）。文字列を睨むのではなく、**実際に供された実体の同一性を毎回検証する**ため、エイリアス化・サイレント差し替えのいずれも検知できる |
| **M-4（起動時の1回確認・司令塔作業）** | 初回運用前に `GET /v1/models` を1回実行し、日付サフィックス付きのスナップショットIDが提供されているかを確認する。**提供されていれば、そちらを `model_id_requested` に差し替えて manifest を再凍結する**（この差し替えは運用開始前の1回に限り許す） |

**選定根拠（4点）**:

1. **決定性（決定打）**。本トラックの停止基準③は「**同一文書・同一モデル・temperature 0** の再実行で2%超のフィールド不一致」である。現行世代のうち **`temperature` を受け付けるのは Haiku 4.5 のみ**で、`claude-sonnet-5` / `claude-opus-5` / `claude-opus-4-8` 系は `temperature` を**送ると 400 で拒否される**（サンプリング制御が撤去されている）。**サンプリングを固定できないモデルは「凍結された抽出器」ではない。** 停止基準を守れるモデルを選ぶのが先である。
2. **タスク適合**。本トラックのタスクは「日本語の適時開示テキストから、文書内に明記された事実を JSON に写す」抽出であり、推論の深さではなく指示追従と表記の一貫性が効く。`CLAUDE.md` が「ニュース・適時開示の分類/抽出（大量・低コスト）は `claude-haiku-4-5`」と定める用途にそのまま当たる。
3. **費用**。§7 のとおり **¥807/月**（Sonnet 5 なら約2倍の ¥1,600/月）。単体では決め手にならないが、本PJの制約（C-6）下では小さくない差である。
4. **拡張思考を使わない**。抽出タスクに thinking は不要であり、非決定性と費用を増やすだけである。`thinking` パラメータを**送らない**（Haiku 4.5 は既定で thinking なし）。

**提供終了時の対応方針（停止基準④との接続・重要）**: Haiku 4.5 は現行世代のうちでは1世代前にあたり、**1年超の運用期間中に提供終了が告知される可能性は小さくない**。本トラックはこれを「避けるべきリスク」ではなく「**必ず訪れる前提の事象**」として扱う。

- 提供終了・または `model_served` の変化を検知した時点で、**黙って後継モデルへ移らない。** 蓄積を停止し、`manifest.json` の `version_boundaries` に境界（最終日・理由・旧モデル実体ID）を記録する。
- 後継モデルは、**本§5.1 の選定基準（とくに「`temperature` を固定できること」）を同じ順序で当て直して**選ぶ。選び直しは新しい manifest（v2）の起票であり、プロンプト・スキーマ・ユニバースは据え置く。
- **v1 と v2 のデータを、境界を明示せずに1本の系列として扱うことを禁じる。** 12ヶ月のフォワード記録が「複数の異なる抽出器の出力の連結」になったことを事後に特定できない状態は、本トラックの価値そのもの（記録の連続性）を壊す（D-14 の趣旨）。

### 5.2 プロンプト

| 項目 | 値 |
|---|---|
| 凍結ファイル | `research/_snapshots/llm_features/frozen/prompt_v1.txt`（3,359字） |
| **SHA-256** | `b24aac1e9557c07ec9f659ec4475c906ab6e792493de6875c94bca8de07ace98` |
| 記録 | ハッシュを **manifest と全出力レコードの両方に記録**する |
| 強制 | 実行のたびにファイルの SHA-256 を再計算し、manifest と**1バイトでも違えば実行しない**（`llm_feature_extract.py` の G-2。検証済み） |
| 送り方 | `system` に置き、`cache_control: ephemeral` を付ける（プロンプトキャッシュ。`CLAUDE.md`「安定部分を前置」に合致） |

**プロンプトが課している制約（抜粋・全文は凍結ファイル）**:

1. 出力は **JSON オブジェクト1個のみ**。
2. **将来の株価・リターン・値動きに関する記述を一切含めない**（予測させない）。
3. **評価・判断を一切含めない**（「好材料」「悪材料」「大幅」「懸念」「想定を上回る」等の評価語を禁止）。
4. **文書に書かれていない数値を推定・補完しない**。見つからない項目は `null` とし `fields_not_found` に記す。
5. **単位換算をしない**（文書記載の単位と数値をそのまま写す）。
6. **外部知識を使わない**（会社の知名度・過去業績・株価水準に関するモデル自身の知識の混入を禁止）。
7. `direction_as_stated`（上方/下方）は **文書自身がそう明記している場合のみ**記入する。**数値を比較してモデルが向きを決めてはならない**（向きの判定は抽出ではなく解釈であり、下流の EXP 側の仕事である）。
8. `factual_summary_ja` は **120字以内・評価語と将来の言及を禁止**。

> **設計上の要点**: 「上方修正か下方修正か」という、候補③が最も欲しい**符号**は、`revision.items[].previous` / `.revised` という**文書記載の2つの数値**として出力される。符号そのものをモデルに判定させないのは、**符号の決め方（どの指標を見るか・営業利益か経常利益か・連結か単体か）が下流のシグナル設計そのものであり、抽出器の中に埋め込むと事前登録の範囲外で設計が固まってしまう**からである。

| **AP-2** | 既に `research/_snapshots/tdnet/` に蓄積済みの **2026-08-06〜2026-09-13 の開示（約9,000件）に遡って抽出することを禁じる。** | 同上（AP-1 の帰結） |
| **AP-3** | 日次・冪等の追記のみ。同一 `doc_id` が `status="ok"` で既に存在すれば再呼び出ししない | G-5 |
| **AP-4** | 出力は `research/_snapshots/llm_features/YYYY-MM-DD.jsonl` に**追記**する。既存行を書き換えない | 実装（append のみ） |
| **AP-5** | `doc_id` = `sha1(開示日 \| 銘柄コード \| 開示時刻 \| PDFファイル名)[:16]` | 実装 |

**なぜ back-fill を禁じるのか（1行）**: モデルの知識カットオフは **2026年5月**であり、それより前の開示に対する抽出は「その後どうなったかを既に知っている状態での抽出」になる。**本トラックの唯一の資産価値は「先読み汚染がないこと」であり、それは1回の back-fill で永久に失われる。** 失われたことを事後に検出する手段は無い（§9 のとおり、漏洩は**存在証明はできても不在証明ができない**）。

**例外はない。** 「今回だけ」「検証のためだけ」を含め、一切認めない。テストが必要な場合は `--dry-run`（API を呼ばない経路検証）を使う。

## 9. 先読み汚染プローブ（重大論点 C-8）— 設計・実施・結果

### 9.1 設計（回す前に固定した値）

| 項目 | 値 |
|---|---|
| 目的 | モデルの知識カットオフ（**2026年5月**）が J-Quants 契約期間（2024-06〜2026-06）の約96%を覆うという C-8 の懸念が、**実測で陽性に出るか**を確かめる |
| 対象モデル | **`claude-opus-5`**（C-8 が名指しする「トレード判断経路に置かれうるモデル」。特徴量抽出器 `claude-haiku-4-5` ではない） |
| 母集団 | PEAD 確認期間 **2025-07-01〜2026-06-21** の決算開示（`DocType` に `FinancialStatements` を含む）、PEAD 候補511銘柄 |
| 間引き | **1銘柄あたり最大1件**（重複出題で見かけの n を膨らませない） |
| **N** | **200件** |
| 層別 | 開示日時点の **時価総額の上位半分 / 下位半分から各100件** |
| 問い | **価格データを一切与えず**、「開示日の**5営業日後**の**終値（円）**はいくらか」を1つの数値で答えさせる（方向ではなく**水準**を問う） |
| **主判定（事前登録）** | 真値の **±2% 以内**に入った回答が **10% を超えたら、漏洩を確定とする** |
| **副次判定（プラセボ対照・事前登録）** | **同一の回答**を、同一銘柄の**無関係な別営業日**（真値日から20営業日以上離れた確認期間内の営業日、シード固定で抽選）の終値に対しても採点する。真値ヒット率 ≈ プラセボヒット率 なら、ヒットは**日付固有の記憶ではなく粗い株価水準の知識**で説明される。**副次であり、主判定の閾値は変更しない** |
| 乱数シード | 20260914（`scripts/leakage_probe.py` に固定） |
| **解釈の制限（事前登録）** | **陽性は漏洩の証明になるが、陰性は不在の証明にならない。したがって本プローブが陰性でも「LLM判断型のバックテストは可能」とは結論しない。** この非対称性こそが、LLM判断型が構造的に検証不能であることの現れである |

> **プラセボ対照を加えた理由（設計時に記録）**: 本PJのユニバースは株価帯 1,000〜3,500円（U-5）に偏っており、**「だいたいの株価水準を知っている」だけで ±2% に当たる確率が無視できない**。主判定の10%閾値だけでは、記憶による漏洩と粗い水準知識を分離できない。プラセボ対照はこれを分離する。

### 9.2 実施手順（本セッションで実際に行った順序）

1. `scripts/leakage_probe.py make-items` を実行し、**価格を一切含まない**出題 `probe/items.json`（200件）と、真値・プラセボ値を**別ファイル** `probe/truth.json` に分離して生成した。
2. 出題（`item_id` / 証券コード / 会社名 / 対象日 / 層）だけを読み、**真値ファイルも当該期間の株価ファイルも開かないまま**、200件の回答を `probe/answers.json` に書き出した。
3. その後に `scripts/leakage_probe.py score` を実行して採点した。

### 9.4 解釈（事前登録した制限の範囲内でのみ）

- **主判定は陰性である**（7.5% ≤ 10%）。
- **プラセボ対照のヒット率（11.5%）が真値のヒット率（7.5%）を上回った。** これは、±2% に入った少数のヒットが**日付固有の記憶ではなく、銘柄の粗い株価水準の知識で説明される**ことを強く示す。**日付を取り違えて採点した方が当たりが多いのだから、当てているのは「その日の終値」ではない。**
- 絶対相対誤差の中央値 13.6% は、**モデルが個別銘柄の日次終値水準を実用的な精度で保持していない**ことと整合する。
- 層別では**下位半分でプラセボ超過が大きい**（7.0% vs 13.0%）。知名度の低い銘柄ほど水準知識が粗く、日付情報がヒットに寄与していないという方向で一貫している。

### 9.5 本結果が**変えないこと**（重要）

| **P-1** | **C-8 は取り下げない。** 事前登録どおり、陰性は不在の証明にならない。**「LLM判断型のバックテストは可能」とは結論しない。** |

### 9.6 本結果が**変えること** — 抽出スコープへの反映

事前登録の抽出スコープ（§5.2）を**緩める方向には変えない**。ただし本結果は、次の設計判断を**支持する**ものとして記録する。

- 本トラックのプロンプトは「**当該文書だけから検証可能な事実に限定**し、外部知識の混入を禁じる」という制約を課している（§5.2 制約6）。仮にプローブが**陽性**であったなら、この制約は**紙の上の宣言にすぎず実効性を疑う**必要があった（水準を記憶しているモデルは、事実抽出のふりをして記憶由来の情報を混入させうる）。**陰性であったことは、制約6 が守られうるという前提を否定しなかった**という限りにおいて、現行スコープの維持を支持する。
- **それでも抽出結果に外部知識が混入していないことを、本プローブは保証しない。** したがって §5.2 の制約6 は**宣言のまま残す**のではなく、次の**下流の検査**で担保する（EXP 起票時に spec へ引き継ぐ申し送り）:
  - **LP-1**: 抽出結果の各フィールドが、**本文テキスト中に文字列として存在する数値**から復元できるかを機械的に照合する（`revision.items[].previous/revised` と `actuals[].value` が対象）。本文に無い数値が出ていれば、それは推定・補完であり制約4・6 の違反である。
  - **LP-2**: `factual_summary_ja` に対する**禁止語リストの機械チェック**（「好」「悪」「大幅」「懸念」「上振れ」「下振れ」「想定」「サプライズ」等）。
  - **LP-1・LP-2 は費用¥0（LLM 呼び出しを伴わない）であり、日次のバッチ後処理として実施できる。** 本事前登録では**実装を義務づけない**（v1 のスコープ外）が、**EXP 起票時の spec には必ず含める**。
