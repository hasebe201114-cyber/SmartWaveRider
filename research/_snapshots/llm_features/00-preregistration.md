## 3. エッジ検定の開始条件（すべて満たすまで EXP として起票しない）

蓄積したデータで**エッジを測ろうとしてよい**のは、次の4条件を**すべて**満たしたときだけである。満たして初めて、通常のリレー（S:prescreen → S:spec → B:実装 → C:判定）に乗せた**新規EXP**として起票する。

| # | 条件 | 閾値 | 出自（本PJで既に確定済みの閾値の再利用） |
|---|---|---|---|
| **ST-1** | 蓄積営業日数 | **≥ 245営業日** | 1年（PJ000001 §6.1 の蓄積規律の年次単位） |
| **ST-2** | 相異なるイベント日数 | **≥ 100日** | EXP-OBS000003 **DS-6 と同値** |
| **ST-3** | 最大単日シェア | **≤ 25%** | EXP-OBS000003 **DS-7 と同値** |
| **ST-4** | 総イベント件数 | **≥ 300件** | EXP-OBS000001 **DS-1 と同値** |

**ST-A（測定単位の明記・重要）**: ST-2〜ST-4 の「イベント」とは、**その新規EXPが事前登録するイベント定義に合致した件数**であり、**蓄積した開示の総件数ではない**。
例: イベント定義が「業績予想の修正開示」なら、蓄積された全開示ではなく、`doc_category = "earnings_forecast_revision"` に該当した件数で ST-2〜ST-4 を測る。
**蓄積の生件数は ST-2〜ST-4 の上限を与えるだけであり、達成を意味しない。** 本PJは EXP-OBS000001 と EXP-OBS000003 の2件連続で、生件数は足りていたのに「相異なるイベント日」で落ちている（C-7）。同じ取り違えを繰り返さないため、本条を明記する。

**ST-B（参考実測・2026-09-14 時点。同日訂正済み）**: U-LLM 271銘柄の開示は **1営業日あたり 20.5件**（**27営業日**・554件の実測。554 ÷ 27 = 20.5）。245営業日で約5,000件が見込まれ、**ST-4（300件）は生件数ベースでは大きな余裕がある。拘束条件になるのは ST-2（相異なるイベント日）である**——イベント定義を絞るほど日数が減るため、EXP 起票時には「イベント定義を絞ること」と「ST-2 を満たすこと」が正面からトレードオフになる。**このトレードオフを、蓄積結果を見てから有利な側に動かすことを禁じる**（イベント定義は prescreen 段階で先に固定し、その後に件数を数える）。

**ST-C（緩和の禁止）**: ST-1〜ST-4 は**本PJが既に確定済みの閾値をそのまま再利用**したものである。**「フォワードだから」「1年待ったのだから」という理由で緩めることを禁じる。** 緩めた瞬間、本トラックは C-7（検出力不足）から逃げただけのものになる。

**なぜ全市場（1営業日 346.7件）ではないか**: §7 の実測コスト算術による。全市場を対象にすると **US$94.5/月 ≒ ¥14,171/月**となり、**C-6 が「払えない」と判定した TDnetアドオン ¥11,000/月 を上回る壁に、別の名前で戻ることになる**。U-LLM 271銘柄なら **¥891/月**で、同じ壁を約1/16の費用で回避できる。

**ユニバース外の開示の扱い（2026-09-14 に運用を確定）**: **271銘柄への限定は LLM による特徴量抽出（有償APIコール）にのみ適用される。** 本文テキストの抽出は `scripts/snapshot_tdnet_text.py` が**全銘柄を対象に** ¥0 で行うため、**テキストは失われない**（日次実行から `--universe-file` オプションを外した。§2 の注記）。ただし **LLMラベルは失われる**（back-fill 禁止のため後から付けられない）。将来ユニバースを広げる判断をした場合、LLMラベルの対象になるのは広げた時点からの新規分だけである。**この非対称性を承知のうえで 271 を選んでいる。**

> **経緯（記録）**: 初版は本項に同じ「テキストは失われない」と書いたが、当時の実装は日次実行に `--universe-file` を付けてユニバース外をスキップする設計であり、**記述と実装が矛盾していた**。司令塔判断により、**記述を実装に合わせるのではなく、運用（全銘柄テキスト抽出）を記述に合わせる**ことで解決した。これは費用¥0の工程であり、§7 の費用見積り・登録上限には影響しない。

**選定根拠（4点）**:

1. **決定性（決定打）**。本トラックの停止基準③は「**同一文書・同一モデル・temperature 0** の再実行で2%超のフィールド不一致」である。**5系（最新世代）に限れば、`temperature` を受け付けるモデルは1つも存在しない**——`claude-opus-5` / `claude-sonnet-5` / `claude-fable-5`・`5-1` 系および `claude-opus-4-8` / `4-7` はサンプリング制御（`temperature` / `top_p` / `top_k`）が撤去されており、**送ると 400 で拒否される**。`temperature` を受け付けるのは、現行モデル表の中では **`claude-haiku-4-5` / `claude-opus-4-6` / `claude-sonnet-4-6` の3つ**であり（`claude-api` スキルの Thinking & Effort 表で確認）、このうち本§の他の基準（②タスク適合・③費用）に最も合致するのが **Haiku 4.5** である。**サンプリングを固定できないモデルは「凍結された抽出器」ではない。** 停止基準を守れるモデルを選ぶのが先である。
   > **2026-09-14 訂正**: 初版は「現行世代のうち `temperature` を受け付けるのは Haiku 4.5 のみ」と書いていたが、これは誤りである（Opus 4.6 / Sonnet 4.6 も受け付ける）。正しくは上記のとおり「**5系に限れば皆無**であり、現行表では3モデルが受け付ける」。**モデル選定の結論（Haiku 4.5）は変わらない。**
2. **タスク適合**。本トラックのタスクは「日本語の適時開示テキストから、文書内に明記された事実を JSON に写す」抽出であり、推論の深さではなく指示追従と表記の一貫性が効く。`CLAUDE.md` が「ニュース・適時開示の分類/抽出（大量・低コスト）は `claude-haiku-4-5`」と定める用途にそのまま当たる。
3. **費用**。§7 のとおり **¥891/月**（単価 input $1.00 / output $5.00 per MTok）。同じ件数を `claude-sonnet-5`（$2.00 / $10.00）で回すと約2倍の **¥1,780/月 ≒ US$11.9** となり、**§7.2 に登録した月額上限 US$10.00 を超える**。単体では決め手にならないが、本PJの制約（C-6）下では小さくない差である。
4. **拡張思考を使わない**。抽出タスクに thinking は不要であり、非決定性と費用を増やすだけである。`thinking` パラメータを**送らない**（Haiku 4.5 は既定で thinking なし）。

**提供終了時の対応方針（停止基準④との接続・重要）**: Haiku 4.5 は**現行モデル表に載る唯一の Haiku（Haiku 系列の最新）**であって「1世代前のモデル」ではない。ただし **Opus / Sonnet / Fable の各系列が既に5系へ進んでいるのに対し Haiku だけが 4.5 に留まっている**ため、**1年超の運用期間中に Haiku の世代更新（および 4.5 の提供終了告知）が起きる可能性は小さくない**。本トラックはこれを「避けるべきリスク」ではなく「**必ず訪れる前提の事象**」として扱う。

- 提供終了・または `model_served` の変化を検知した時点で、**黙って後継モデルへ移らない。** 蓄積を停止し、`manifest.json` の `version_boundaries` に境界（最終日・理由・旧モデル実体ID）を記録する。

1. 出力は **JSON オブジェクト1個のみ**。

5. **単位換算をしない**（文書記載の単位と数値をそのまま写す）。
6. **外部知識を使わない**（会社の知名度・過去業績・株価水準に関するモデル自身の知識の混入を禁止）。
7. `direction_as_stated`（上方/下方）は **文書自身がそう明記している場合のみ**記入する。**数値を比較してモデルが向きを決めてはならない**（向きの判定は抽出ではなく解釈であり、下流の EXP 側の仕事である）。

> **設計上の要点**: 「上方修正か下方修正か」という、候補③が最も欲しい**符号**は、`revision.items[].previous` / `.revised` という**文書記載の2つの数値**として出力される。符号そのものをモデルに判定させないのは、**符号の決め方（どの指標を見るか・営業利益か経常利益か・連結か単体か）が下流のシグナル設計そのものであり、抽出器の中に埋め込むと事前登録の範囲外で設計が固まってしまう**からである。

| パラメータ | 値 | 備考 |

> **`temperature = 0` は「ビット単位で同一の出力」を保証しない（重要・2026-09-14 追記）。** `temperature = 0` はサンプリングを最尤トークンの選択に寄せるだけであり、API として出力の完全再現性を約束するものではない。同一入力でも、サーバ側のバッチ構成・並列度・浮動小数点演算の非結合性・推論実装やハードウェアの差によって、ごく低い確率で異なるトークンが選ばれうる。

> **したがって停止基準③の閾値は「不一致率 0%」ではなく「2%以下」として登録してある**（§8-③）。この2%の許容幅は「多少のブレは許す」という運用上の妥協ではなく、**`temperature = 0` が決定性を保証しないという技術的事実に対する、回す前に固定した許容幅**である。**結果を見てからこの幅を広げることを禁じる**（N-L3）。逆に、不一致率がこの幅を超えた場合は「サンプリングの揺らぎでは説明できない変化（実体モデルの差し替え・プロンプト経路の変化・入力テキストの非決定性）が起きた」と読み、停止してバージョン境界の調査を行う。

## 9. 先読み汚染プローブ（重大論点 C-8）— 設計・実施・結果

> ## ⚠ 本プローブは API 実測ではない（結果を読む前に必ず読むこと）
>
> **本プローブは Anthropic API を1回も呼んでいない。実行環境に `ANTHROPIC_API_KEY` が無いため、`claude-opus-5` への API 呼び出しの代わりに、プローブを設計した本人——本セッションを実行している `claude-opus-5` エージェント自身——が200件に回答した（自己採点）。** `probe/answers.json` と `probe/result.json` の `administration` フィールドに `"self-administered by the running claude-opus-5 agent (no API key available)"` として記録してある。
>
> **この留保が意味すること**:
>
> - **対象モデルは C-8 が名指しするモデルと同一だが、呼び出し文脈が清浄ではない。** 本セッションの文脈には本PJの資料（ユニバース・株価帯 U-5・PEAD の設計など）が入っており、清浄な API 呼び出しとは条件が異なる。**結果の解釈にあたり、この差を割り引くこと。**
> - **設計者＝回答者であるため、無自覚な手心（当てにいく／外しにいく）を構造的に排除できていない。** これは B(実装)と C(判定)を分ける本PJの鉄則（`PJ000002` §1）に照らせば**そもそも避けるべき構造**であり、本プローブの結果を「独立検証を経た測定」として扱ってはならない。
> - **回答の順序だけは担保されている**: 200件の回答は、真値ファイル（`probe/truth.json`）も当該期間の株価ファイルも**一切開かないまま**先に書き出した（§9.2）。その順序は本セッションの記録で追跡できる。
> - **したがって §9.3 の数値は「API実測値」ではなく「自己採点の参考値」である。** `ANTHROPIC_API_KEY` の供与後（D-11a）、**清浄な API 呼び出しで再実施することを申し送る**。
>
> **主判定の結論（NOT_CONFIRMED／C-8 を取り下げない）は、この留保があっても変わらない**——陰性は不在の証明にならないという事前登録の制限（§9.5 P-1）により、そもそも陰性から何かを結論する設計になっていないためである。

### 9.4 解釈（事前登録した制限の範囲内でのみ）

> **2026-09-14 訂正**: 初版は「プラセボ（11.5%）が真値（7.5%）を上回った → 記憶による漏洩ではないことを**強く示す**」と書いていたが、**これは統計的に過大な主張である**（McNemar 正確検定で両側 p = 0.229、有意差なし）。下記のとおり訂正する。**主判定の結論（NOT_CONFIRMED・C-8 を取り下げない）は変わらない。**

- **主判定は事前登録した閾値を下回った**（7.5% ≤ 10%）。**ただし「真の漏洩率が10%未満である」ことを示したわけではない**——15/200 の Wilson 95%信頼区間は **[4.6%, 12.0%]** で**閾値10%を含む**（さらに、真の率が10%だと仮定したとき 15件以下が観測される確率は 0.143 であり、10% を棄却できていない）。**事前登録した判定規則に従って「漏洩は確定しなかった」と言えるだけである。**
- **真値ヒット率（7.5%）はプラセボヒット率（11.5%）を上回らなかった。** これは**記憶による漏洩とは整合しない**方向の観測である。**ただし両者に統計的有意差はない**（真値のみ的中13件 vs プラセボのみ的中21件、McNemar 正確検定 両側 p = 0.229）。**n = 200 では検出力が不足しており、「ヒットが日付固有の記憶ではなく粗い株価水準の知識で説明される」ことを断定はできない。** 言えるのは「**そう解釈しても矛盾しない**」までである。
- 絶対相対誤差の中央値 13.6% は、**モデルが個別銘柄の日次終値水準を実用的な精度で保持していない**ことと整合する。
- 層別では下位半分でプラセボ超過が大きい（7.0% vs 13.0%）が、**層別に分けると各層 n = 100 でさらに検出力が落ちる**ため、この差から傾向を読むことはしない（方向としては上記と一貫している、という以上のことは言わない）。
- **検出力についての申し送り**: 本プローブを「漏洩の不在」の根拠として再利用しようとする者が現れた場合、**n = 200・±2% という設計では、閾値10%前後の漏洩率を分離できるだけの検出力が無い**ことを本項が示している。**再実施する場合は、n を増やすか判定閾値を設計し直すこと**（それでも §9.5 P-1 の非対称性は残る）。
