## 1. コンセプト

日経225を起点とする日本株に対し、テクニカル指標による統計シグナルと、ニュース・適時開示のLLM解釈を組み合わせ、**3〜10営業日保有のスイングトレード**を自動執行するエンジンを構築する。発注は三菱UFJ eスマート証券の kabu STATION API を用いる。

### 1.1 trading-app-v2 から輸入する設計思想（最重要）

本プロジェクトはゼロからの試行錯誤を繰り返さない。trading-app-v2 が2026年6〜7月に8連敗で確定させた以下の診断を**初期条件として受け入れた上で設計する**。

1. **「価格由来の特徴量から方向を予測する」エッジ族は効率化の床に達している。**
   trading-app-v2 の8連敗はすべてこの族の変奏であり、ブレッド（銘柄数=OBS000030・頻度=OBS000031）を実際に増やした2実験ではICがゼロ〜負に崩れた。原因は「ブレッド不足」ではなく**エッジ族そのものの枯渇**と再診断されている。

2. **②の職務は「単一の予測器を磨くこと」ではなく「複数の直交するエッジ（スリーブ）を生成・配分すること」である。**
   個別スリーブの採否は単体Sharpeではなく**ポートフォリオへの限界寄与**（既存主軸との低相関＋合成でのSharpe改善／DD削減）で判定する。単体Sharpeは参考値に降格する。

3. **成功基準は「回す前」に数値で確定する（HARKing防止）。** 結果を見てから基準を緩めない。

4. **予測単位とパイプライン統合の両方を測定する。** 片方だけは禁止（OBS000025型＝予測単位◎でパイプラインで死ぬ罠、OBS000027/029/031型＝予測単位からして無エッジ）。

5. **選定（探索）データと確認（未見）データを分離する。** 選定で見つけた優位が確認で消えるのが常態（OBS000019/028型の過学習）。

6. **不採用も負の結果として台帳に残す。** 偽陽性回避の資産であり、重複起票の防止装置でもある。

### 1.2 本プロジェクトが trading-app-v2 と異なる点

- **市場が違う**ため、暗号資産で枯れたエッジ族が日本株でも枯れているとは限らない。ただし「テクニカルで方向を当てる」という生成過程は同一であり、**事前確率は低いものとして扱う**（→ 4章 C-3）。
- **ニュース／適時開示という非価格情報が構造的に豊富**である。日本株は決算短信・適時開示（TDnet）が制度として時刻付きで配信され、暗号資産にはないイベント境界が存在する。trading-app-v2 で③LLM層が不発（OBS000014/027）だった主因は「価格由来シグナルの上に足し算した」ことであり、本プロジェクトでは**③を独立したエッジ源泉の候補として扱う**（②の補助ではない）。
- **制度的制約が厳しい**（単元株・値幅制限・取引時間・信用規制）。これはリスクであると同時に、24/365市場にはない**構造的なエッジ源泉**（イベントドリブン、需給の期日性）でもある。

## 2. 全体アーキテクチャ（7層構成）

trading-app-v2 の7層アーキテクチャを日本株向けに移植する。

```
① データ層（kabu STATION API / J-Quants / TDnet・ニュース）
    ↓
② シグナル生成・配分層（コア・アルファ生成＆配分層）
    ↓                    ↑
③ LLM特徴量抽出層（ニュース・適時開示のスコア化）
    ↓
④ 統合判断層（方向・強さ・確度）
    ↓
⑤ リスク管理・ポジションサイジング層
    ↓
⑥ 執行層（kabu STATION API 発注・約定管理）
    ↓
⑦ 評価・チューニング層（層横断で常時稼働）
```

### 2.1 各層の詳細

#### ① データ層 — `src/data_layer/`

- **日足・財務**: J-Quants API（株価四本値、財務諸表、決算発表予定日、投資部門別売買状況）
- **リアルタイム板・歩み値**: kabu STATION API（`/board/{symbol}`, PUSH配信）
- **適時開示**: TDnet（決算短信・業績修正・自己株買い等）※取得方式は STEP0 で確定
- **ニュース**: 取得元は STEP0 で確定（要決定事項 → 10章）
- 取得データはすべて `data/raw/` に日付付きで永続化し、**再取得なしで同じバックテストが再現できること**を必須とする

#### ② シグナル生成・配分層 — `src/signal_layer/`

trading-app-v2 の職務定義改訂を最初から適用する。**この層は「複数の直交するスリーブを生成し、配分する」層である。**

- **スリーブ候補（STEP2で検証）**: 現行の4戦略パターン A〜D はいずれも「価格由来テクニカルで方向を当てる」同族であり、**4本の独立した賭けではない**（→ 4章 C-3）。STEP1 でこれを非価格系スリーブ候補（イベントドリブン、需給、③LLM単独）へ再編する。
- **配分**: 選定期間で凍結した逆ボラティリティ・ウェイト。フルKellyは禁止、フラクショナルKelly（f ≤ 0.5）を上限とする。
- 決定的でバックテスト可能であることを最優先。パラメータは `research/config/parameter-set.json` でバージョン管理する。

#### ③ LLM特徴量抽出層 — `src/llm_layer/`

- 決算短信・業績修正・適時開示・ニュースを、**数値・カテゴリのフラグに変換する**役割に限定する。トレード可否そのものをLLMに判断させない。
- 出力例: センチメントスコア（−100〜+100）、影響持続期間の推定（日数）、イベント種別分類、サプライズ度（会社予想比・コンセンサス比）
- **判断根拠を全てログ化**し、事後に妥当性検証できるようにする（`logs/live_trading/llm_analysis.log`）。
- **trading-app-v2 の教訓**: ③を②の上に「足し算」した OBS000014/027 は2条件とも増分価値なしで打ち切られた。本プロジェクトでは③を**独立スリーブとして予測単位から単独で検定する**（②の土台なしで方向一致率・IC・permutation p値を測る）。ここで単独エッジが実証できないものは、④でどう組んでも救えない。
- 利用モデル: 大量・低コストの分類/抽出は `claude-haiku-4-5`、少数の高難度な統合判断は `claude-opus-5`。

#### ④ 統合判断層 — `src/decision_layer/`

- ②の（方向・強さ・確度）と③のフラグを組み合わせて最終シグナルを生成。
- 初期はルールベース（③が重大ネガティブイベントを検知したら②のシグナルを縮小／見送りにする veto 方式）。
- 将来的には統合ロジック自体もバックテスト対象とする。

#### ⑤ リスク管理・ポジションサイジング層 — `src/risk_layer/`

日本株固有の制約が最も強く効く層。詳細は 8章。

- 単元株（100株）の離散性を前提としたサイジング
- 委託保証金率・最低委託保証金の監視
- 値幅制限（ストップ高／安）で損切が執行できないケースのハンドリング
- **決算発表日を跨がない**ことを制約条件として組み込む（→ 4章 H-3）
- ドローダウン上限による自動停止（サーキットブレーカー）

#### ⑥ 執行層 — `src/execution_layer/`

- kabu STATION API による発注・訂正・取消・約定確認
- 寄り付き／引け／ザラ場のどこで執行するかは戦略ごとに固定し、バックテストの約定前提と一致させる
- API 障害時のフェイルセーフ（発注済みポジションの保護を最優先、新規発注は停止）

#### ⑦ 評価・チューニング層 — `src/evaluation_layer/`

- 予測単位の評価（非重複サンプル・permutation 検定・有効n）
- パイプライン統合の評価（Sharpe・最大DD・レジーム別分解）
- フォワード較正の日次冪等追記（back-fill による水増しを禁止）

## 3. 日本株ならではの制約（暗号資産版との差分）

**本章は本プロジェクト最大の設計インプットである。** trading-app-v2 のロジックをそのまま移植できない箇所を明示する。

| 項目 | 暗号資産（trading-app-v2） | 日本株（本PJ） | 設計への影響 |
|---|---|---|---|
| 取引時間 | 24時間365日 | 前場 9:00–11:30 / 後場 12:30–**15:30**<br>（2024-11-05 の東証取引時間延長後。15:25–15:30 はクロージング・オークション） | オーバーナイト／連休ギャップが構造的リスク。既存 README の「15:00 クローズ」は**要修正** |
| 建玉単位 | 小数可（連続） | 原則 **単元100株** | ポジションサイズが離散。最小単位が資本に対して大きい（→ 4章 C-2） |
| レバレッジ | 数倍〜数十倍 | 信用取引・委託保証金率30%以上 → **最大約3.3倍** | 本PJでは1.5〜2.0倍に自主制限 |
| 最低証拠金 | 実質なし | 制度信用の**最低委託保証金30万円** | 初期資本30万円と同額＝評価損発生と同時に新規建て不可（→ 4章 H-4） |
| 値幅制限 | なし | ストップ高／ストップ安 | **損切注文が約定しない日がある**。バックテストは必ずこれを模擬する |
| 空売り | 自由・対称 | 制度信用・逆日歩・空売り規制銘柄 | ショートのコストが非対称。ロング／ショート同条件の前提は誤り |
| API 可用性 | クラウド常時 | kabu STATION（Windows常駐アプリ）の**ローカルPC依存** | 単一障害点（→ 4章 H-2） |
| 市場データ | 無料APIが豊富 | J-Quants は有料。無料プランは**12週間遅延** | ランニングコスト（→ 4章 H-1） |
| イベント境界 | 曖昧 | 決算・適時開示が**時刻付きで制度配信**（TDnet） | ③LLM層にとって構造的な優位。本PJ独自のエッジ源泉候補 |

## 4. 着手前に解決すべき重大論点

**回す前に解決する。** 以下を未解決のまま STEP2 のバックテストに進んではならない。

### CRITICAL

#### C-1. 損切／利確比が逆転しており、現行設計の期待値はマイナス

既存 `research/STEP1-planning.md` §5 のリスク管理ルールは **損切 −2.0% / 利確 +1.5%** である。これはリスクリワード比 0.75（損切幅のほうが大きい）を意味する。

損益分岐勝率 = 損切幅 ÷（利確幅＋損切幅）= 2.0 ÷ 3.5 = **57.1%**

これを既存の4戦略の期待勝率に当てると（手数料・スリッページ除く、1トレードあたり%）:

| 戦略 | 期待勝率 | 期待値の計算 | 期待値 | 判定 |
|---|---|---|---|---|
| A: モメンタム追従 | 55% | 0.55×1.5 − 0.45×2.0 | **−0.075%** | マイナス |
| B: 平均回帰 | 58% | 0.58×1.5 − 0.42×2.0 | +0.030% | ほぼゼロ |
| C: トレンドフォロー | 52% | 0.52×1.5 − 0.48×2.0 | **−0.180%** | マイナス |
| D: ボラティリティ先行 | 60% | 0.60×1.5 − 0.40×2.0 | +0.100% | ほぼゼロ |

さらに往復のスプレッド＋スリッページを保守的に 0.10〜0.20% とすると、**B・D も期待値マイナスに転落する**。

現行設計は**シグナルの精度以前に、決済ルールの時点で負けが確定している**。

**対策（STEP1 で確定させる）**:
- 利確幅 > 損切幅 となるよう再設計する（例: 損切 −2.0% / 利確 +4.0% → 損益分岐勝率 33.3%）
- またはトレーリングストップにより利益を伸ばす設計へ変更する
- いずれにせよ**「損切幅・利確幅・想定コスト」を先に固定し、そこから必要勝率を逆算してから**シグナル設計に入る

**決着（2026-09-13）**

司令塔判断3により、決済ルールは**トレーリングストップ（(b)）**を採用。固定の利確幅は置かない。

ただし採用はこれで終わりではなく、以下4点を A設計相当の spec で**回す前に数値固定する**ことを必須条件とする（未固定のまま STEP2 のバックテストに入ってはならない）。

1. 初期損切幅
2. トレール発動水準（含み益がどこまで乗ったらトレールを開始するか）
3. 追随幅（高値からどれだけ戻したら手仕舞いか）
4. どの足でトレールを更新し、どの価格で約定したとみなすか

**警告**: トレーリングストップは決済価格が経路依存（保有期間中の高値・安値の推移そのものに依存）になるため、日足だけの検証では高値掴みの誤差（日中の高値でトレール判定したのに翌日始値でしか約定できない、等）が出る。§6.2 の日足ベース検証はこの誤差を過小評価しうる点に注意する。

#### C-2. 「1銘柄2万円 × 5銘柄」は単元株制度下で実現不可能

既存 `research/STEP1-planning.md` §5 のポジション設計は 1銘柄あたり最大2万円・同時5銘柄である。しかし日本株は原則 **単元100株** で、日経225採用銘柄の1単元は概ね 20〜40万円帯にある。**2万円で買える日経225銘柄はほぼ存在しない。**

資本30万円・レバレッジ2.0倍で建玉枠60万円とすると:

| 想定 | 1単元の金額 | 同時保有可能数 |
|---|---|---|
| 株価 6,000円 | 60万円 | 1銘柄 |
| 株価 3,000円 | 30万円 | 2銘柄 |
| 株価 1,200円 | 12万円 | 5銘柄 |

同時5銘柄を成立させるには**株価1,200円以下の銘柄だけでユニバースを組む**必要があり、日経225ではセクター分散が成立しない。

**対策（STEP1 で選択する）**:
1. ポジションサイズを 1銘柄15〜30万円へ引き上げ、同時保有を 2〜3銘柄に絞る（分散は効かなくなる。1銘柄の失敗が資本に直撃するためリスク管理の再設計が必須）
2. ユニバースを日経225から TOPIX Small / 中低位株へ変更し、単元金額を下げる（流動性と信用取引対応の再確認が必要）
3. 単元未満株（S株）を使う ※ただし**信用取引不可・リアルタイム約定不可**のため、本PJの設計とは両立しない
4. 運用資本を増やす（司令塔判断）

**この選択は C-1 とセットで期待値を再計算するまで確定できない。**

**決着（2026-09-13）**

司令塔判断1により運用資本を**100万円**へ増額（レバレッジ2.0倍・建玉枠200万円）。これにより本論点は解消する。

| 想定 | 1単元の金額 | 同時保有可能数（建玉枠200万円） |
|---|---|---|
| 株価 2,000円前後 | 20万円 | 5〜8銘柄 |

株価2,000円前後の銘柄を中心にユニバースを組めば、単元未満株を使わずに同時5〜8銘柄の分散が成立する。ユニバース選定は判断2（TOPIX500 から流動性・信用取引可否で150〜200銘柄に絞る）と合わせて 10章 #2 を参照。

#### C-3. 4戦略 A〜D は「独立した4本の賭け」ではなく同族である

既存 README は A（MACD+RSI）／B（ボリンジャーバンド+CCI）／C（移動平均クロス+ADX）／D（ATR+Stochastic）の4パターンを並行検証し、有望な2つを本番採用するとしている。

しかしこの4つは**すべて「日足の価格・出来高から算出したテクニカル指標で将来の方向を当てる」という単一のエッジ族**の変奏である。これは trading-app-v2 が8連敗で枯渇を確定させた族と生成過程が同一である。

4本並べても、それは**独立した4回の試行ではなく、相関の高い1つの賭けを4通りに言い換えたもの**にすぎない。「4つ試せばどれか当たる」という期待は、多重検定によって偽陽性を拾う確率だけを上げる。

**対策（STEP1 で再編する）**:
- A〜D は「テクニカル方向予測スリーブ」**1本**として扱い、その中で最良の1構成を選ぶ（4本ではなく1本の在庫）
- 残りの実験予算は**直交するエッジ源泉**へ振り向ける。日本株固有の候補:
  - **イベントドリブン**: 決算サプライズ後のドリフト（PEAD）、業績修正、自己株買い発表
  - **需給**: 信用残・裁定残の偏り、投資部門別売買動向、需給イベント（リバランス、TOPIX浮動株比率見直し）
  - **③LLM単独スリーブ**: 適時開示テキストのみから方向を予測（価格由来特徴量を一切使わない）
- スリーブの採否は**限界寄与**（既存スリーブとの低相関＋合成でのSharpe改善／DD削減）で判定する

**決着（2026-09-13）**

司令塔判断7（時間軸＝併存構成）により、テクニカル方向予測スリーブは**主軸1時間足・エントリー判断15分足**の1スリーブとして再編する。非価格系スリーブ（PEAD・需給）は日足のまま据え置く。

これは「A〜Dは4本ではなく1本の在庫として扱う」という上記の再編方針自体を変えるものではない。時間軸を日足から1時間足/15分足に変えても生成過程は「価格由来テクニカルで方向を当てる」ままであり、**事前確率は引き続き「低」として扱い、主軸として期待しない方針を維持する**。

なお、この時間軸選択は新たな重大論点 C-4（1時間足・15分足の過去データが無償では入手できない）を発生させている。詳細は C-4 を参照。

#### C-4. 1時間足・15分足の過去データが無償では入手できない

司令塔判断7（時間軸＝併存構成。テクニカル系スリーブは主軸1時間足・エントリー判断15分足）の採用に伴い、新たに発生した論点。

- J-Quants が無償プランで提供するのは日足四本値・前場後場四本値・財務・投資部門別売買状況などであり、**1時間足／15分足の分足時系列は提供範囲に含まれない**という認識である（※断定は避ける。STEP0 タスク 0-9 の実機確認で確定させる）。
- kabu STATION API は現在値・板・歩み値の**リアルタイム配信**であり、**過去の分足履歴を遡って取得する口がない**。
- 結果として、司令塔判断4（ニュース・適時開示の取得元＝無償の範囲で最大限）と同じ制約の下では、分足データは「今日から自前で貯める」以外に選択肢がなく、**§6.2 の選定2015-2022／確認2023-2026というデータ分割は、テクニカル系スリーブに関しては成立しない**（自前蓄積を始めてから選定・確認を切り出すには数年を要する）。

**対策の選択肢（STEP0 タスク 0-9 の実測後に司令塔が再判断する）**:
1. 分足データを有料で調達する
2. テクニカル系スリーブの検証を、自前蓄積後のフォワード中心の検証に切り替える（選定/確認の事前分割を諦め、蓄積しながら評価する）
3. 日足で代理検証（プロキシ検証）を行ってから、実運用時に分足へ移す

**この論点は判断7とセットで発生したものであり、非価格系スリーブ（PEAD・需給、日足のまま）には影響しない。**

#### 参考: 1時間足の採用と姉妹プロジェクトの負の資産（OBS000031）の関係

判断7で採用する主軸の時間軸（1時間足）は、`research/portfolio-ledger.md` に記録された trading-app-v2 **OBS000031「短時間足高頻度化（1h 平均回帰）＝手数料ゼロのグロス段階で平均マイナス」**と時間軸が一致する。

CLAUDE.md の鉄則（「同型のアイデアを起票する場合は、なぜ日本株では結論が変わりうるのかを prescreen で明示すること」）により、これは**起票禁止ではない**。テクニカル方向予測スリーブ（1時間足）を実際に回す際は、prescreen で以下のような日本株固有の構造的差分を明示することを条件とする。

- 値幅制限（ストップ高／安）
- 寄り付きの板寄せ（オークション方式）
- 引け前の需給の偏り
- 昼休みによる取引の分断（前場／後場）

暗号資産（24時間365日連続取引）にはこれらの構造が存在しないため、OBS000031 の結論がそのまま日本株にも当てはまるとは限らない。ただし C-3 決着に記載の通り、**事前確率は引き続き「低」として扱う**。

### HIGH

#### H-1. ランニングコストが期待リターンを構造的に圧迫する

| 項目 | 月額（概算） | 備考 |
|---|---|---|
| J-Quants API（有料プラン） | 数千円 | プラン選定と実額は STEP0 で要確認 |
| Claude API（ニュース分析・Haiku 4.5） | 約 $10 | 30銘柄×5件/日、1件あたり入力1.5K/出力0.3Kトークン想定 |
| Claude API（シグナル統合・Opus 5） | 約 $20 | 1日20回、1回あたり入力5K/出力1Kトークン想定 |
| **合計** | **約 7,000〜10,000円** | |

運用資本30万円に対し、月7,000〜10,000円は **月率 2.3〜3.3%** に相当する。README が掲げる期待月間リターン 3〜5% の**半分以上がコストで消える**。

**対策**:
- バックテスト期間中は J-Quants 無料プラン（12週間遅延）で足りるか検証し、有料化のタイミングを遅らせる
- LLM 呼び出しを日次バッチに集約し、プロンプトキャッシュを効かせる（銘柄リスト・分析指示など安定部分を前置）
- **本質的には、このコスト構造は運用資本30万円と釣り合っていない。** コストに見合う規模まで資本を増やすか、自動化範囲を絞るかを司令塔が判断する（→ 10章）

**決着（2026-09-13）**

司令塔判断1（運用資本100万円）により、上記の月額7,000〜10,000円というコストは**月率 約0.7〜1.0%**へ低下し、README の期待月間リターン3〜5%との比較では大幅に改善する。

**警告**: ただし司令塔判断7（時間軸の高頻度化＝1時間足主軸・15分足エントリー）により**取引コストが増える**方向に働く。往復0.15%×月10〜15往復と試算すると、取引コストだけで**月1.5〜2.3%**に達する。資本増によるコスト率低減（API費用側）が、取引頻度増によるコスト増（売買コスト側）で相殺されうる点に注意し、STEP1の実コスト実測でこの試算を検証すること。

#### H-2. kabu STATION API の常駐PC依存が単一障害点になる

kabu STATION API は kabu STATION（Windowsアプリ）を起動したPC上で `localhost` に立つローカルAPIである（本番 18080 / 検証 18081）。クラウドから直接叩けない。

- 営業日 8:50〜15:30 のあいだ**PCとアプリを起動し続ける必要がある**
- Windows Update の自動再起動、電源断、ネットワーク断がそのまま取引停止に直結する
- APIトークンは1日1回の発行が必要

既存 `.env.example` の `KABU_API_BASE_URL=https://kabusapi.kabu.com/v1` は誤りであり、**STEP0 で実機検証して修正する**。

**対策**: 電源・ネットワークの冗長化方針、起動監視と異常時通知、ポジション保有中にAPIが落ちた場合の手動手順書（`docs/B-トレーダ向けアプリ活用編`）を STEP0 で整備する。

#### H-3. 決算・適時開示によるギャップリスクが資本に対して過大

3〜10営業日保有のスイングトレードでは**必ず翌日への持ち越しが発生する**。決算発表を跨いだ場合、寄り付きで −10% のギャップは珍しくない。

1銘柄20万円のポジションで −10% のギャップ = **−2万円 = 資本30万円の6.7%**。同時3銘柄が同方向に被弾すれば **−20%** で、ドローダウン上限15%を一発で突破する。

**対策（必須ルールとして⑤に実装）**:
- **決算発表予定日を跨ぐポジションを持たない**（J-Quants の決算発表予定日APIで前日引けまでに強制手仕舞い）
- 同一セクターへの同時建玉に上限を設ける
- 連休前のポジション縮小ルール

#### H-4. 制度信用の最低委託保証金30万円と初期資本30万円が同額

制度信用取引の最低委託保証金は30万円である。初期資本がちょうど30万円だと、**評価損が1円でも出た時点で新規建てができなくなる**。

既存 `research/STEP1-planning.md` §5 は「実現資本（証拠金）20万円／バッファ7万円／テスト費用3万円」としているが、証拠金20万円では制度信用の最低額を下回り建玉できない。

**対策**: 資金配分を再設計する。最低委託保証金を常に上回るバッファを確保するか、一般信用／現物に切り替えるかを STEP0 で確定する。

**決着（2026-09-13）**

司令塔判断1により運用資本を100万円へ増額したことで、制度信用の最低委託保証金30万円に対し**バッファ70万円**が確保され、本論点は解消する。

## 5. ゴールと KPI

### 5.1 North Star

**未見データ（確認期間）で、コスト控除後の年率 Sharpe ≥ 1.0 を、90日フォワード較正を通過した構成で達成する。**

trading-app-v2 の North Star（Sharpe 1.5）より低い水準に置く。理由は、日本株スイングでは取引頻度が低く、資本制約から同時保有数も少ないため、統計的な有効n が構造的に小さいこと。過大な目標は HARKing の誘因になる。

### 5.3 スリーブの採否基準（限界寄与）

trading-app-v2 PJ000001 §5.4 を踏襲する。個別スリーブの採否は**単体Sharpeではなくポートフォリオへの限界寄与**で判定する。

- **G1（予測単位）**: 確認期間で方向一致率が有意（permutation p < 0.05）かつ手数料ゼロのグロス段階で平均が正
- **G2（パイプライン）**: コスト控除後の純リターンが確認期間で正
- **G3（低相関）**: 既存スリーブとの相関 |ρ| < 0.3
- **G4（限界寄与）**: 合成後の Sharpe が既存構成 +0.15 以上、**または** 最大DD が既存構成 −5pt 以下

**G1 未達は即打ち切り。** trading-app-v2 の OBS000027/029/031 はいずれも G1 で棄却され、そこから先を回す価値はなかった。

### 5.4 Kill 基準（明示）

以下に該当した時点で、そのスリーブは廃棄し `research/portfolio-ledger.md` の「不採用」へ負の資産として記録する。

- 確認期間の予測単位でグロス平均が負（コストを議論する以前にエッジが不在）
- 選定期間で見つけた優位が確認期間で消失（過学習）
- 予測単位は良いがパイプライン統合で悪化（trading-app-v2 OBS000025型）
- 成功基準を事後に緩めないと通らない（HARKing）
