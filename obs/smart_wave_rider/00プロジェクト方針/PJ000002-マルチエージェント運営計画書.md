## 1. なぜ体制を分けるのか

本プロジェクトのマルチエージェント体制は「組織ごっこ」を目的としない。唯一かつ最大の目的は、

> **B（実装）とC（判定）を別人格にして、自分の実装を甘く採点させない**

ことである。これは姉妹プロジェクト trading-app-v2 が **8連敗（OBS000018/022/025/027/028/029/030/031）** を経て確立した、偽陽性対策の中核そのものである。1人（または1つのエージェント）が「実装して、自分でよかったと判定する」構造では、以下が構造的に起こる。

- 好結果が出た瞬間に検証の目が甘くなる（確証バイアス）
- 成功基準を結果を見てから緩める（HARKing）
- 選定データでの好成績を未見データでの再現と混同する（過学習の見逃し）

これらはすべて trading-app-v2 の8連敗で実際に発生した罠であり、`research/portfolio-ledger.md` の「姉妹プロジェクトから輸入した負の資産」に記録されている。**B実装チームとC品質チームを別エージェント（別プロセス・別コンテキスト）として起動し、Cには「好結果を壊しにいく」ことを職務として与える**のは、この罠を構造的に防ぐためである。

## 2. 体制構成: 縮小版3体（現在）

CLAUDE.md は将来像として S/A/B/C/D/E の6体を想定して書かれているが、**実験がまだ1件も起票されていない現状の負荷に見合わせ、まず以下の3体から開始する**。

| 役割 | エージェント名 | モデル | 担当範囲 |
|---|---|---|---|
| S 戦略チーム | `chief-strategist` | opus | 目利き・**設計（A兼務）**・台帳とブリーフの管理 |
| B 実装チーム | `quant-researcher` | sonnet | spec に忠実な実装。生データのみ出力 |
| C 品質チーム | `adversarial-reviewer` | opus | 偽陽性の最終防波堤。採用/不採用の宣告 |

モデルはいずれもエイリアス指定とし、Anthropic側のモデル更新に自動追従させる（固定バージョンにピン留めしない）。

### 2.1 縮小の内容と対応関係

| CLAUDE.md 上の6体 | 本計画書での扱い |
|---|---|
| S 戦略チーム(chief-strategist) | そのまま存続。**加えてA設計官の責務（spec確定）を兼務** |
| A 設計チーム(strategy-architect) | **独立エージェントとしては当面起動しない**。責務はSが兼務 |

| C 品質チーム(adversarial-reviewer) | そのまま存続 |

## 3. 各エージェントの役割・入力・出力・禁止事項

### 3.1 S 戦略チーム（chief-strategist / opus）

| 項目 | 内容 |
|---|---|
| 役割 | 日本株市場の目利き、prescreenの起票、**spec（実験仕様）の確定**（A設計官を兼務）、成功基準を回す前に数値で固定、`portfolio-ledger.md` と `STRATEGY-BRIEF.md` の管理 |
| 入力 | 司令塔から渡されたテーマ、`portfolio-ledger.md`（過去の採否）、`PJ000001` の市場観・重大論点、C品質チームの判定結果 |
| 出力 | `EXP-OBSxxxxx/00-prescreen.md`、`EXP-OBSxxxxx/00-spec.md`（成功基準を数値で固定）、`portfolio-ledger.md` / `STRATEGY-BRIEF.md` の更新案 |
| 禁止事項 | 結果を見てから成功基準を緩める（HARKing）。価格由来の方向予測を無条件に有望と扱う（事前確率は低いものとして扱う） |

### 3.2 B 実装チーム（quant-researcher / sonnet）

| 項目 | 内容 |
|---|---|
| 役割 | spec に忠実にバックテスト・検証を実装し、**予測単位とパイプライン統合の両方**の生データのみを出力する |
| 入力 | `EXP-OBSxxxxx/00-spec.md`、既存の `scripts/` `src/` |
| 出力 | `EXP-OBSxxxxx/10-result/`（`prediction-unit.json` / `pipeline.json` / `params.json` / `cost-model.json` / `run.log`。`_templates/result.readme.md` 準拠） |
| 禁止事項 | 解釈・採否判断を書く。spec にない条件を勝手に追加する。結果が悪いからとパラメータを事後に変える |

### 3.3 C 品質チーム（adversarial-reviewer / opus）

| 項目 | 内容 |
|---|---|
| 役割 | 好結果を壊しにいく偽陽性の最終防波堤。採用/不採用/差し戻し/保留を宣告する |
| 入力 | `EXP-OBSxxxxx/00-spec.md`、`10-result/`、必要に応じた独立再検算 |
| 出力 | `EXP-OBSxxxxx/20-review.md`（`_templates/review.template.md` のチェックリストに全項目回答） |
| 禁止事項 | Bの自己申告を鵜呑みにする。HARKingの見逃し。予測単位かパイプラインの片方だけで判定を確定する |

### 3.4 当面Claude Code本体が代行する責務（D・E）

| 元の役割 | 代行内容 |
|---|---|
| D デプロイチーム | Cが「採用可」を宣告し、かつ**司令塔の最終GO**が出た実験についてのみ、`src/` への反映・`research/config/parameter-set.json` の確定・コミットを実施する |
| E 進行チーム | OBS採番、`EXP-OBSxxxxx/` の作成、`ACTIVE.md` の更新、OBSファイルのフォルダ移動（実装中/解決済）、引き継ぎ書の更新 |

## 4. リレーのフロー

```
司令塔がテーマを渡す
        │
        ▼
   S: 目利き（prescreen） ── 却下なら終了・記録のみ
        │ GO
        ▼
   S: 設計（spec確定） ── 成功基準を数値で固定（HARKing防止）
        │
        ▼
   B: 実装（予測単位＋パイプラインの生データ出力）
        │
        ▼
   C: 検証（採用可 / 不採用 / 差し戻し / 保留 を宣告）
        │
        ├─ 差し戻し ──→ S(spec) または B(実装) に戻る
        │
        ▼ 採用可
   司令塔の最終GO
        │
        ▼
   （D代行）本番反映 ──→ （E代行）OBS移動・台帳更新・引き継ぎ更新
```

**このリレーは全自動ではない。** オーケストレーター（Claude Code 本体）が各サブエージェント（S/B/C）を対話の中で順に起動し、成果物の受け渡し（前段の出力ファイルを次段の入力として渡すこと）を仲介する運用である。

## 5. 司令塔（ユーザー）の必須操作は2点のみ

CLAUDE.md の開発方針に「スマホで指示することが多いため、ユーザのオペレーションは極小とする」とある通り、本体制は**司令塔の判断ポイントを意図的に2点に絞る**ことを設計原則とする。

1. **① S にテーマを渡す**（何を目利きしてほしいかを一言伝える）
2. **② C の宣告に対し、本番反映のGOを出す**（採用可の宣告に対して「反映してよいか」を最終決裁する）

状況把握はこの2点の判断のためだけに必要な最小限の情報に絞り、以下の2枚で完結させる。

- `research/ACTIVE.md`（誰待ちかの機械的な信号機）
- `research/STRATEGY-BRIEF.md`（何で勝とうとしていて、今どこで詰まっているかの作戦ブリーフ）

司令塔がコンソールを開いて途中経過を逐一確認する必要がないよう、進捗の可視化・要約はオーケストレーター側（E代行）が能動的に更新する。

## 6. 鉄則（CLAUDE.md §運営体制の運用手順化）

| 鉄則 | 運用手順への落とし込み |
|---|---|
| 成功基準は回す前に数値で確定する（HARKing防止） | Sが `00-spec.md` に数値基準を書いた時点でロックし、B実装後・C判定後に基準文言を書き換えない。書き換えが必要な場合は新しいEXPとして起票し直す |
| 予測単位とパイプライン統合の両方を測定する | `result.readme.md` の要求どおり `prediction-unit.json` と `pipeline.json` の両方が揃っていない場合、Cは自動的に「差し戻し」とする |
| 選定（探索）データと確認（未見）データを分離する | spec の「選定/確認プロトコル」欄を必須記入とし、Cのチェックリスト#3で選定→確認の再現性を独立に確認する |
| B（実装）とC（判定）は必ず別エージェント | quant-researcher と adversarial-reviewer は別サブエージェント定義として起動し、同一の対話コンテキストで自己採点させない |
| 採用ゲートは人間 | Cの「採用可」はあくまで推薦。本番反映（D代行の起動）は司令塔の明示的なGOなしには実施しない |
| 不採用も負の結果として台帳に残す | 不採用・保留の判定はすべて `research/portfolio-ledger.md` の該当表とPJ000001の変更履歴（該当あれば）に追記する。破棄しない |

## 8. 3体 → 6体への拡張条件

以下のいずれかに該当した時点で、該当する役割を独立エージェントとして分離することを検討する。分離するか否かは司令塔が判断する（自動昇格はしない）。

| 分離候補 | 拡張条件（目安） |
|---|---|
| A 設計チーム（strategy-architect）の独立 | 同時に検討中の実験（EXP）が複数件並行し、Sが目利きと仕様確定を1人で回すことがボトルネックになったとき。または spec の設計精度（成功基準の妥当性・HARKing耐性）そのものをSとは別の視点でレビューする必要が生じたとき |
| D デプロイチーム（integration-deploy）の独立 | 「採用可」の実験が本番反映され、STEP2以降で本番運用ロジックが継続稼働を始め、反映作業（コード変更・段階的投入・ロールバック判断）が単発のコミット作業を超えて専任の注意を要するようになったとき |
| E 進行チーム（archivist-pm）の独立 | 実験（EXP-OBSxxxxx）の起票・完了サイクルが定常的に回り始め、OBSフォルダ移動・リンク修正・引き継ぎ更新・`ACTIVE.md`更新などの事務作業量がオーケストレーターの都度対応では追いつかなくなったとき |

拡張時は本ドキュメントを改訂し（変更履歴に追記）、`.claude/agents/` に該当エージェント定義（`strategy-architect.md` / `integration-deploy.md` / `archivist-pm.md`）を追加する。CLAUDE.mdの想定利用モデル（A・B・D=sonnet／E=haiku）はその時点で有効化する。
